# 自動回覆改版：不再像 FAQ 機器人

> **狀態：已完成實作。** 不需要 migration。
>
> 這份**改掉了 [auto-reply.md](auto-reply.md) 的兩個原有決定**：
> 移除反問編號選項、放寬「模型一字都不能生成」。
>
> ⚠️ **上線後要自己到話術頁把舊的開場白與結尾語清掉**（見最後一節）。

## 問題

上線後實際看下來，回覆太制式，而且預設客人一定是在「問問題」。

### 1. 開場與結尾都是固定的

`answer_full` 是「開場白 + {答案} + 結尾語」，`answer_short` 雖然短，
但尾巴一樣寫死「還有其他問題都歡迎再告訴我們！」。

**固定的尾巴就是罐頭感的另一半** —— 真人回答完就回答完了，
不會每一則都補同一句。客人連著問三題，就看到三次一模一樣的結尾。

### 2. 不確定時丟編號選項

`clarify` 模板寫死選項清單，等於**強迫客人從題庫裡挑一項**。
客人明明講的是別的事，卻被要求在 1. 2. 3. 裡選。

### 3. 話術在指示客人該怎麼回

同一段模板：「**麻煩您回覆編號**，或直接描述一下您遇到的狀況」。

客人本來想怎麼講就怎麼講，系統不該規定格式 —— 真人客服不會這樣講話。

### 4. 每一句都要對應到題庫某一則

system prompt 第一句是「判斷客人的問題對應到哪一則」。
不管客人說什麼，模型都只能在「命中／不確定／沒有」三選一。

客人說「我想加一台虛擬機」——這是**需求**不是問題，題庫當然沒有，
模型判低信心，系統就丟出編號選項。客人的感受是「它聽不懂我在說什麼」。

客人說「好」「收到」——也會被拿去比對題庫，然後同樣丟出選項。

## 已確認的方向

| 項目 | 決定 |
|------|------|
| AI 能不能生成文字 | **可以生成「承接句」**（回應客人的那一兩句），**答案本體仍是題庫原文，一字不改** |
| 固定結尾語 | **預設拿掉**。答案講完就結束，不每則都補同一句 |
| 編號選項 | **完全移除**。不確定就說稍等並轉人工 |
| 指示客人怎麼回 | **一律不准**。客人想直接說明、想怎麼描述都可以 |
| 是不是每句都要選題庫 | **不是**。需求、寒暄本來就不該查題庫，直接說明即可 |
| 轉人工變多 | **可以接受**。初期本來就會多，題庫隨著回填長大之後會越來越準 |

最後一條是整個設計的定調：**寧可轉人工，不要硬答**。
門檻設保守，答錯的成本遠高於多轉一次人工。
而且每轉一次人工，就是一次把題庫補起來的機會。

## 新的判斷方式

模型除了挑題目，還要先判斷**客人這則訊息是哪一種**：

| intent | 說明 | 怎麼處理 |
|--------|------|----------|
| `question` | 在問一件事（多少錢、怎麼用、可不可以） | 查題庫。有把握才答，否則轉人工 |
| `request` | 提需求（想加機器、要開通、希望改成…） | **完全不查題庫**。承接 + 轉人工 |
| `chat` | 寒暄、道謝、確認（好、收到、謝謝） | 簡短承接，**不開求助單** |

`request` 不查題庫是重點 —— 需求本來就不是題庫該回答的東西，
硬去比對只會撈出不相干的答案，然後逼客人從裡面挑。

### 輸出改成

```json
{
  "intent": "question | request | chat",
  "item_id": 12,
  "confidence": "high | low",
  "opening": "好的，了解您需要再加一台虛擬機，我馬上請同仁為您安排"
}
```

### 決策表

| intent | 條件 | 送給客人 | 開求助單 |
|--------|------|----------|----------|
| question | high 且題目存在 | `{opening}` + 題庫答案原文 | 否 |
| question | 其他 | `{opening}`（表示正在確認） | **是** |
| request | 一律 | `{opening}` | **是** |
| chat | 有需要回應 | `{opening}` | 否 |
| chat | 只是「好」「收到」 | **不回**（`silent`） | 否 |

**五種情況裡只有第一種會帶題庫答案。** 其餘四種都是直接說明，
不硬塞任何題庫內容進去。

`silent` 是新增的：客人回一句「好」，系統再回「好的，隨時為您服務」很煩。
這種情況閉嘴才自然。不回的紀錄仍會寫 log，用量照算。

### 一則訊息長怎樣

```
好的，這部分的費用是這樣的：        ← AI 寫的承接句，每次不同

{題庫答案原文，一字不改}

-A                                  ← 署名
```

**沒有固定開場白，也沒有固定結尾語。** 承接句負責開頭，
答案講完就結束。後台的話術模板仍然可以編輯（想加東西還是加得回去），
但**預設是空的**。

### 順帶確認：本來就沒有用 Telegram 的「引用回覆」

查過 `AutoReplyService::send()`，`sendReply()` 的 `$replyToId` 傳的是 `null`，
自動回覆一直都是直接發訊息、沒有引用客人那一則。這部分不用改。

## 承接句的護欄

這是唯一讓模型自由發揮的地方，所以限制要寫死在 prompt，**並且後端再驗一次**：

- **最多兩句、60 字以內**
- **不准指示客人該怎麼回覆**。不能說「請回覆編號」「請提供以下資訊」「麻煩告知…」，
  客人想怎麼講就怎麼講
- **不准出現任何規格、價格、數字條件、時間承諾**
  （「三天內完成」「一台 500」這種一律不行）
- **不准對需求做裁決** —— 不能說「可以」「沒問題」「我們有提供」，
  那是同仁才能決定的事
- ⚠ **不准替別人承諾**「馬上請同仁處理」（2026-10-06 加，見下方）
- ⚠ **牽涉到錢的事不准說「收到」**（2026-10-05 加，見下方）
- **不准改寫或重述題庫答案**，答案原文自己會接在後面
- **不要每次都用同一句開頭**，客人連著問會看出來

後端驗證（`AutoReplyService`）：

- 超過長度 → 不用，退回模板
- 命中黑名單（保證／一定／免費／沒問題／請回覆／請提供…）→ 退回模板並記 log
- 模型沒給 opening → 退回模板

### ⚠ 不准替別人承諾「有人會來處理」

**實際出過的包（2026-10-06）**：客人說「老闆，有蝦嗎」，被判定為**寒暄**，
模型回：

> 老闆好～這邊馬上請同仁為您處理。 -A

**但寒暄那條路不會開求助單** —— 根本沒有任何人收到通知，客人就一直等。
需求方的話：「不應該請同仁處理後，沒開問題單」。

⚠ **肇因又是 prompt 自己教的**，而且是同一個洞的第二次：

```
能不能做、怎麼做，都是同仁才能決定的事。你只能表示「馬上請同仁處理」。
                                              ^^^^^^^^^^^^^^^^ 這裡
```

下面「『收到了』在金流語境等於認帳」那節已經記下教訓
「prompt 舉的例子會被當範本照抄」，但改的時候**只換掉了被回報的那一句**，
沒有回頭檢查其他例子在新架構下還成不成立。

而「馬上請同仁處理」在 2026-10-06 之後**永遠是假的**：轉人工已經不回覆
客人了（見 [[auto-reply]]），所以承接句出現的三種情況 —— 命中答案、追問、
寒暄 —— **都不會有人來處理**。

修法照舊是兩層：

| 層 | 改了什麼 |
|---|---|
| prompt | 拿掉那個例子，並寫明「沒有『等一下有人會來』這回事，講了就是騙客人」 |
| 黑名單 | 補 `請同仁`／`請人員`／`請專人`／`轉給同仁`／`幫您轉`／`會有人` |

⚠ **被擋下之後，寒暄那條會變成「什麼都不回」**（`filled($opening)` 不成立
→ `SILENT`）。那是對的：寧可不說話，也不要給一個不存在的承諾。

⚠ **轉人工那條不受影響** —— 承接句被擋只是少了一句話，`WAIT` 照樣開求助單
（驗證有確認）。

### ⚠ 客人「把資料給我們」時被當成寒暄 → 已讀不回

**實際出的包（2026-10-06）**：我方先說「請對方提供串接資訊給我們」，
客人照做貼了一整段（帳號、密碼、API KEY、後台網址、Server IP），
**AI 完全沒有回應，也沒有開求助單**。

病根是 intent 只有三種：

```
question  在問一件事
request   提需求
chat      寒暄、道謝、確認
```

**「提供資料」不屬於任何一種。** 模型只能硬塞，塞成 `chat` 就會被放掉 ——
而那正是最不該漏的一種訊息：客人把東西交出來了，卻像被已讀不回。

prompt 補上判準：**客人把資料給我們時算 `request`**（帳號、密碼、API KEY、
網址、訂單號、整段設定值，或是在回答我們先前問他的事情），一律轉人工。
並明寫「**這種訊息絕對不能判成 chat**」。

走 `request` → `WAIT` → `openTicket()`，所以會進支援群組。

> ⚠ 沒有新增 intent 類型 —— `request` 的處理本來就是「不查題庫、轉人工」，
> 正好是要的行為。加第四種要動 schema、常數、決策表，划不來。

#### 萬一還是判錯成 chat

`SILENT` **刻意不標記已回覆**（`dispatchResult()` 的註解寫得很清楚）。

⚠ **但那道網 2026-10-06 沒了**：未回覆告警（`telegram:alert`）已移除，
而判成 chat/SILENT 時**不會開求助單**，所以接手的求助單超時提醒也撈不到它。
判錯成寒暄的訊息現在沒有任何自動告警，只能靠客服看對話列表發現。
缺口記在 [[remind-escalation]]。

真的漏掉時，可以從 log 撈：`自動回覆判定為寒暄，只回一句、不開求助單`
與 `自動回覆判定不需回應`。

#### ⚠ 順帶：客人貼的密碼會進 AI 的 prompt

這則訊息含帳號密碼與 API KEY，而 `buildHistory()` 會把近期訊息（含這則）
當脈絡送進 Claude Code CLI，也就是送到 Anthropic。訊息本身也照常存在
`telegram_message` 與 log 裡。

這是既有行為、客人自己傳的，不是這次改動造成的，但**值得知道**：
要求客人改用其他管道傳敏感資料的話，得另外處理。

### ⚠ 承接句不要複述問題，也不要每次同一個句型

**實際出的包（2026-10-06）**，連著三則：

```
關於 U 與卡卡餘額顯示的部分，這邊說明如下～
關於回調主機 IP 的部分，這邊跟您說明～
關於新增代理的密碼設定，這邊跟您說明～
```

兩個毛病疊在一起：

1. **句型完全一樣** —— 客人一眼看出是機器拼的
2. **那句話沒有任何資訊** —— 只是把客人的問題重講一次。他知道自己問了什麼

prompt 原本只有一句「不要每次都用同一句開頭」，太弱，而且**沒告訴模型
去哪裡看自己說過什麼**。其實脈絡裡本來就有（`buildHistory()` 會把
outbound 寫成「客服：…」帶進去），只是沒叫它看。

補了三條：

- **不要把客人的問題再講一次**（「關於 OOO 的部分」）
- **先看脈絡裡「客服：」那幾則是怎麼開頭的**，不要再用同一個句型
- ⚠ **想不到新講法時，填 null 比硬湊一句更好** ——
  不是每一則都需要開場白，答案本身夠清楚就讓它自己說

最後那條是關鍵：**允許它不說話**。有時有、有時沒有，反而比每則都硬加一句
更像真人。

> ⚠ 刻意**不舉替代句型的例子** —— [[auto-reply]] 那兩次（「收到了」、
> 「馬上請同仁處理」）的教訓是**模型會把 prompt 裡的例子當範本照抄**，
> 舉了就等於換一個新的罐頭。

### ⚠ 題庫答案自帶問候時，承接句不要再問候一次

**實際出的包（2026-10-06）**：

```
老闆好～關於系統費的部分，這邊為您看一下     ← 承接句
老闆您好，稍等系統費請人員為您說明 -A        ← 題庫答案
```

兩次問候。模型挑答案時**看得到整份題庫**（答案都在 system prompt 裡），
所以它知道那題的開頭長什麼樣 —— 只是 prompt 沒告訴它要看。

補一條規則：**先看你挑的那則答案是怎麼開頭的**，已經有問候就不要再問候，
直接切入或填 null 讓答案自己開場。

> 這跟「轉同仁答案」那次的問題同源，但解法不同：那邊模型看不到答案
> （答案是同仁當下打的），所以要額外呼叫一次；這邊答案本來就在 prompt 裡，
> 只要叫它去看就好，**不必多花一次呼叫**。

### ⚠ 「稍等」被存進題庫 = 以後沒有人會知道

同一次對話暴露的更嚴重問題：那則題庫答案是
**「老闆您好，稍等系統費請人員為您說明」** —— 那不是答案，是過渡用語。

它會這樣進去：同仁在支援群組回「稍等，請人員為您說明」，然後按
「回覆並加入題庫」。於是「系統費怎麼算」的標準答案就變成一句「稍等」。

**後果比看起來嚴重**：往後每個問系統費的客人都會命中這題、收到「稍等」，
而且因為是**命中題庫**，`replyWithItem()` 那條路**不開求助單** ——
沒有任何人知道有人在問，客人就一直等。

防法只能在源頭：求助訊息上多一句提醒

```
⚠️ 按「加入題庫」之後，這個答案會自動回給往後問同樣問題的客戶，
   所以「稍等」「我問一下」這類過渡用語請不要寫進去。
```

> 程式擋不了這個 —— 「這句算不算答案」沒有可靠的判準，硬擋只會擋掉
> 同仁真正想存的內容。發現題庫裡有這種答案，到後台改掉或停用那一題。

### 寒暄的判斷維持原樣

「老闆，有蝦嗎」會被判成寒暄 —— 一度想把判準收緊成「只要在問有沒有／
能不能／多少就算 question」，**但需求方否決了**：

> 不對，還是要判斷寒暄

收緊的代價是「老闆在嗎」「有人在嗎」這種**本質是寒暄的問句**也會開求助單，
同仁會收到一堆沒有內容的單。判準維持原本的「寒暄、道謝、確認」。

所以寒暄判錯時的狀況是：**客人收到一句招呼（或什麼都沒有），不開求助單**。
那可以接受 —— 不可接受的是上面那件事（說了「請同仁處理」卻沒人處理），
那個已經擋掉了。

補了一行 log（`自動回覆判定為寒暄，只回一句、不開求助單`）——
這條路徑原本完全沒有紀錄，事後要查「為什麼這句沒進支援群組」只能用猜的。
覺得某類訊息常被判錯，先從這行 log 撈出來看。

### ⚠ 「收到了」在金流語境等於認帳

**實際出過的包（2026-10-05）**：客人貼了付款截圖說「老闆 這邊先直接儲值
不讓你為難」，AI 回：

> 感謝老闆體諒，**這邊收到了**，會請同仁協助後續處理🙏 -A

語氣完全沒問題 —— 但在那個語境，「收到了」會被讀成**我們確認收到這筆錢**。
款項要會計對過帳才算數，由系統先認帳，事後對不上會變成糾紛。

⚠ **直接肇因是 prompt 自己教的。** 那條規則原本寫著：

```
能不能做、怎麼做，都是同仁才能決定的事。你只能表示「收到了、馬上請同仁處理」。
                                              ^^^^^^^ 這裡
```

模型照做而已。**寫 prompt 時順手舉的例子，模型會當成範本照抄** ——
舉例要挑在所有語境下都安全的說法。

修法兩層（prompt 是請求、黑名單是保證）：

| 層 | 改了什麼 |
|---|---|
| prompt | 拿掉那個例子，改成「馬上請同仁處理」；另加一條：客人說已付款／轉帳／儲值或貼匯款截圖時，不能說「收到了」「已收到」「已入帳」，只能說「已經請同仁為您核對」 |
| 黑名單 | 補上 `收到了`／`已收到`／`已入帳`／`已到帳`／`已收款`／`款項已收`／`已儲值`／`已加值`／`已補點`／`已確認` |

⚠ **黑名單是字串包含比對，分不出語境**，所以會誤殺「已收到您的訊息」
這種本來沒問題的句子。那是**刻意的取捨**：誤殺的代價只是退回固定話術
（安全網，等於改版前），漏放的代價是替公司認帳。

> 退回的固定話術是「您好，感謝您的詢問 🙏…」，對「客人告知已付款」的語境
> 其實不太搭（他不是在詢問）。但不會出錯，而且 prompt 改好之後黑名單
> 應該很少被觸發 —— 真的常觸發就表示 prompt 沒講清楚，要回去改 prompt
> 而不是加更多禁語。

prompt 有快取（`auto_reply.prompt_cache_key`），但只有 **300 秒**，
改完最多五分鐘生效，不用手動清。

**退回模板**就是現在的話術，所以最壞情況等於現況，不會更糟。

## 支援群組要帶上 AI 的猜測

轉人工時，在支援群組的求助訊息裡多附一段（**只有自己人看得到**）：

```
🤖 AI 判斷：需求類（request）
　 最接近的題庫：#12 虛擬機規格與費用（信心不足）
```

兩個用處：同仁不必從頭看就知道客人大概要什麼；
而且一眼看得出「這題題庫沒有」，回完順手按「加入題庫」，下次就準了。

這正是「初期多轉人工、題庫越長越準」那條路的加速器。

## 話術模板要改什麼

| 欄位 | 變更 |
|------|------|
| `answer_full` / `answer_short` | **預設改成只有 `{答案}`** —— 不含開場白也不含結尾語 |
| `clarify_full` / `clarify_short` | **移除**（編號選項沒了，「麻煩您回覆編號」跟著消失） |
| `wait_full` / `wait_short` | **保留，降級為 fallback** —— 模型沒給 opening 或被護欄擋下時才用 |
| `support_full` / `support_short` | **預設也拿掉結尾語**，理由同上 |

`app_setting` 裡既有的 clarify 資料**留著不刪**（不讀就沒有影響），
不為了這個跑一支 migration。

⚠️ seeder 只在第一次寫入，**已經存在的模板不會被 seeder 覆蓋**。
所以上線後要**自己到話術頁把舊的開場白與結尾語清掉**，
否則會變成「AI 承接句 + 舊開場白 + 答案 + 舊結尾語」，比現在更囉唆。

## 連鎖影響

- **`auto_reply_pending` 欄位不再使用**：那是記反問候選 id 的，反問沒了就用不到。
  欄位留著不動（不 ALTER），程式面停止讀寫
- **`AutoReplyService::takeCandidates()`、`CLARIFY` 決策**：移除
- **`auto-reply:test` 的 `--pending` 參數**：移除
- **`GREETING_GAP_MINUTES`（30 分鐘換短版）**：保留但幾乎用不到 ——
  開場白與結尾語都拿掉之後，full 與 short 的差別本來就不大了

## 實測結果

```
$ php artisan auto-reply:test "我想再加一台虛擬機"

【決策】沒把握或是需求，說稍等並轉內部群組
intent   : request（提需求）
item_id  : null
opening  : 了解，您想再增加一台虛擬機的需求已經收到，馬上請同仁為您處理。

【實際會送給客人的訊息】
了解，您想再增加一台虛擬機的需求已經收到，馬上請同仁為您處理。 -A

【支援群組會多看到的 AI 判斷】
🤖 AI 判斷：需求
```

改版前這句話會得到「請問您是指以下哪一項？1. 2. 3.」。

```
$ php artisan auto-reply:test "好，謝謝"

【決策】不需要回應，完全不回
intent  : chat（寒暄）
opening : （沒給）
```

決策表六條路徑也逐一驗過，其中兩條最關鍵：

- **需求類即使模型給了 item_id 與 high 信心，仍然不查題庫**、一律轉人工
- 承接句寫「沒問題，保證三天內完成」會被黑名單擋掉，**退回固定話術**

## 上線後補修：客人連續問第二個問題會消失

上線當天就踩到。客人 14:47 問「後台打不開」，AI 回了稍等；
14:48 再問「提單 50000 顯示失敗」——**完全沒有回應，支援群組也沒有收到**。

兩個限制疊在一起造成的：

1. **`replyWait()` 的 5 分鐘冷卻**（`WAIT_COOLDOWN_MINUTES`）。
   那個 `return` 擋在 `openTicket()` **前面**，所以不只沒回覆客人，
   連求助單都沒開 —— 同仁根本不知道有人問過
2. **`openTicket()` 的「同群組只能一張未處理單」**。
   就算修好第一點，第二個問題仍然不會進支援群組

結果是最糟的組合：**客人以為有人在處理，實際上沒有人知道**。

### 改法

- **移除 wait 冷卻**（連同 `WAIT_COOLDOWN_MINUTES` 常數與 `isWaitOnCooldown()`）。
  冷卻本來是為了避免「稍等」一再重複顯得敷衍，但承接句每次都不一樣，
  這個理由已經不存在。客人問一次就回一次，本來就是客服該做的事
- **改成每個問題各開一張單**，只擋「一模一樣的問題」
  （`findOpenByQuestion()`）—— 客人手滑重複貼、等不及又問一次，
  開第二張只是洗版，沒有新資訊；但**不同的問題一定要各自開單**

判斷準則：**漏掉客戶的問題，比內部群組多幾則訊息嚴重得多。**

## 上線步驟

1. `php artisan optimize`（constants 與 config 有改）
2. **到「對客話術」頁把舊的開場白與結尾語清掉** —— 見下方

### ⚠️ 話術一定要自己清

`AppSettingSeeder` 只在**設定不存在時**才寫入，**已經存在的模板不會被覆蓋**。

所以現有環境的話術仍然是舊的「您好，感謝您的詢問 😊 …… 很高興為您服務！」。
不清掉的話，客人會收到：

```
AI 承接句        ← 新的
您好，感謝您的詢問 😊   ← 舊模板的開場白
{答案}
很高興為您服務！       ← 舊模板的結尾語
```

**比改版前更囉唆。** 命中題庫那格建議只留 `{答案}`，話術頁上也加了這段提醒。

## 風險

- **承接句是模型寫的，就有幻覺空間**。護欄把它限制在「不含事實的一兩句」，
  且黑名單 + 長度檢查會退回模板。但無法 100% 保證 ——
  這是換取自然度必須接受的代價，上線後要抽看實際送出的內容
- **intent 判斷會錯**。把 question 判成 chat 最危險（客人問了卻被略過），
  所以 `silent` 的門檻要非常嚴：只有純寒暄、且訊息很短時才允許
- **轉人工變多**（已接受）。支援群組的負擔會上升，但那是題庫成長的來源
- **舊模板要手動清乾淨**，否則新舊包裝疊在一起（見上面的 ⚠️）

## 補充確認

| 項目 | 決定 |
|------|------|
| `silent` | **要做**。客人說「好」「收到」時完全不回，後台仍看得到那則訊息 |
| 承接句能不能主動 | **不行**。一律不做任何裁決或承諾，全部轉人工詢問 |
| 署名 | 承接句 + 答案是同一則訊息，仍是一個 `-A` 結尾，不會變兩個 |

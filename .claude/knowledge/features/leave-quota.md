# 假別與特休額度

**需求方 2026-11-05**：

> 「內勤管理的人員管理這邊，我要按照他的年資去計算他特休的天數，然後我請假
> 部分要可以選他是請什麼假別，可以選特休、病假、事假，然後用小時計算，
> 特休請完就不能請了，然後要在個人每日出勤狀況這邊要標注他當天是請什麼假別，
> 報表的打卡報表這邊請假也要註明。」

**狀態：已實作（v3.74，2026-11-05）。**
**⚠ 上線前置：跑 migration `2026_11_05_000001`（加 `type` 與 `minutes`）。**

## 特休級距（需求方 2026-11-05 已指定）

| 年資 | 特休 |
|---|---|
| 6 個月以上、未滿 1 年 | 3 日 |
| 1 年以上、未滿 2 年 | 7 日 |
| 2 年以上、未滿 3 年 | 10 日 |
| 3 年以上、未滿 5 年 | 14 日 |
| 5 年以上、未滿 10 年 | 15 日 |
| 10 年以上 | 每年加 1 日，加到 30 日為止 |

⚠ 這張表放 `config/constants.php`，**不要寫死在程式裡** —— 級距是法規，
改了要能只改 config。10 年以上那段要用公式（`15 + (年資 - 9)`，上限 30），
不要展開成二十列。

## 現在長什麼樣

| 現況 | 說明 |
|---|---|
| `leave_request` 表 | **沒有假別欄位**。只有 `is_full_day`／`start_time`／`end_time`／`status` |
| 統計 | `AttendanceService::summariseLeaves()` 把整天假算「天」、時段假算「小時」，**兩者不互通** |
| 個人每日出勤狀況 | 有「請假」欄，只顯示「請假中」或時段，**不分假別** |
| 打卡報表 | 有「請假」欄，顯示 `N 天 / N 小時`，**不分假別** |
| 年資 | `StaffResource` 與 `AccountResource` **各算一份**（都從 `hired_at` 推） |

## ⚠⚠ 最大的結構問題：天與小時現在是兩套，無法相加

需求是「用小時計算」而特休額度是「日」。現在整天假只累加天數、時段假只累加
小時，**兩個數字從來沒有被換算成同一個單位**——
所以「特休剩幾小時」目前算不出來。

這是這個需求真正的工程量所在，不是加一個下拉選單。

要做的是：**所有假單都換算成「分鐘」存下來**，顯示時再換回日／小時。
一日等於幾小時必須先定義（見待釐清 1）。

⚠ `summariseLeaves()` 有三個呼叫端（出勤明細、打卡報表、Telegram 報表），
改它等於同時改三個出口 —— 這是好事（數字不會分岔），但要一起驗。

## 裁示結果（需求方 2026-11-05）

| 題目 | 裁示 |
|---|---|
| 一日幾小時 | **輪班 12 小時、固定班 8 小時**（依該員出勤模式）|
| 年度制 | **週年制**（到職日起算）|
| 未休完 | **遞延一年** |
| 病假／事假 | **第一版只管特休**，兩者照樣選、照樣記錄，但不擋 |
| 扣額度時機 | **核准時扣**；申請時先檢查「剩餘 − 待審核中」夠不夠 |
| 既有假單 | 另開「**未分類**」，不扣特休 |
| 剩餘特休顯示在 | 內勤管理人員列表、請假申請表單、個人每日出勤狀況（三處都要）|

### ⚠ 條文裡兩個容易漏掉的細節（需求方 2026-11-05 貼的勞動部說明）

**一、6 個月以上未滿 1 年那 3 日，使用期間不是一整年。**

> 「但其工作六個月以上一年未滿者，為取得特別休假權利後**六個月**之期間。」

也就是從滿 6 個月那天起算六個月（到滿 1 年為止），不是從到職日起算一年。

**二、留職停薪得不併入年資。**

⚠ 系統目前**沒有留職停薪的概念**，年資一律從 `hired_at` 算到今天。
有人留停過的話，這裡算出來的年資會偏多、特休也會偏多 ——
這是**已知限制**，要處理得先有留停的資料。

### ⚠ 遞延的簡化（實作限制，要知道）

正確的遞延要逐年度記帳（這一期用掉的是「上期遞延來的」還是「本期的」）。
不開新資料表的話做不到完整帳本，所以採用：

```
遞延 = max(0, 上期額度 − 上期已用)
可用 = 本期額度 + 遞延
剩餘 = 可用 − 本期已用
```

⚠ 這在「連續兩年都沒休完」時會**略為高估**（上上期的遞延已經失效，
但上期已用沒有被歸到那個池子）。勞基法只允許遞延一年，所以差異有上限。
要完全正確就得開一張 `leave_quota_year` 表逐期記帳。

## 實作時踩到／刻意處理的

### ⚠⚠ PHP 的陣列 key 不能是浮點數

級距表原本寫成 `0.5 => 3`，而 PHP 會**無聲地**把它轉成 `0 => 3` ——
於是「年資 >= 0」對每個人都成立，**到職第一天就拿到 3 日特休**。
實測印出年資 0.2 算出 3 日才抓到。寫成 `'0.5'`（字串 key）才對。

整數那幾格不受影響，所以只有那一格要引號 —— 這種「只有一格有問題」的
狀況最容易看漏。

### ⚠ 又是 select 漏欄位（這個 Repository 的第四次）

`getAllCsUsersWithDetail()` 沒有撈 `work_mode`，而「一日幾小時」就是看它。
不補的話 `dayMinutes()` 會把每個人都當成輪班，**固定班的人額度憑空多一半**，
而且不會報錯。

前三次：`findByTelegramUserId()` 漏 `level`、同一支漏 `project_ids`、
`getActiveForDropdown()` 漏 `project_ids`。

> **在 `UserRepository` 加任何「依使用者屬性判斷」的功能之前，
> 先確認那個欄位在不在 select 裡。**

### 假別白名單擋在三層

1. `config/rules.php` 的 `LEAVE_TYPE_IN`（Request 驗證）
2. `LeaveRequestService::resolveType()`（認不得的一律當事假）
3. 表單的下拉本身只有三個選項

⚠ 三層都**沒有 `unclassified`**：那是改版前舊資料的標記，放行的話使用者
就有一種「不扣任何額度」的假可以送。

### 「還沒有特休」與「有特休但用完了」要分得開

`period_start` 是 null 代表前者。後端刻意**不把它夾成 0** —— 兩者都印 0
的話，主管會以為新人把特休請光了。人員列表那一格因此是「—」而不是「0」。

## 實測

**額度計算（假 Repository，不碰 DB）**

| 檢查 | 結果 |
|---|---|
| 年資 → 日數（含 0.2／0.49／0.5 邊界與 10 年以上公式）| 全對，24 年封頂 30 日 |
| 一日分鐘數 | 輪班 720、固定班 480 |
| 週年制期間 | 滿 6 個月那期只到滿 1 年前一天（半年）|
| 跨期間的假單 | 按天拆，只算落在本期的那幾天 |
| 遞延 | 上期 7 日未休 → 本期多 84 小時 |
| 還沒滿 6 個月／沒填到職日／未來到職日 | 都回 0 且 `period_start` 是 null |

**端到端（申請流程）**

| 檢查 | 結果 |
|---|---|
| 整天假的分鐘數跟著出勤模式 | 輪班 2 天 = 1440 分、固定班 = 960 分 |
| 時段假含跨午夜 | 22:00~02:00 = 240 分 |
| 假別白名單 | `unclassified` 與亂填都被擋成事假 |
| 特休用完再請 | 擋下，訊息帶「只剩 0 小時」|
| 同樣超額改請病假 | 通過（第一版只擋特休）|
| 待審核中的也算進去 | `canAfford` 正確扣掉 |

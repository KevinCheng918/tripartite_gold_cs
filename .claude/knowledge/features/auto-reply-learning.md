# 假陰性回收：候選按鈕與問法樣本

## 現況

已完成，**待跑 migration**。

## 問題

客人問的其實題庫有答案，模型卻沒比對出來。

以前求助單只給同仁一行純文字：

```
🔔 題庫裡找不到答案
問題：這是什麼錯誤呢
🤖 AI 判斷：提問
　 最接近的題庫：#23 商戶餘額沖正（信心不足）
```

同仁看到這行之後，只有兩條路：

1. 回後台翻一百多題，找到那題，複製答案，貼回來 —— 麻煩到沒有人會做
2. 自己打字答一遍，然後按「回覆客人並加入題庫」

**第二條路就是題庫長出重複題目的成因。** 2026-09-23 一次刪掉 17 題重複題，
其中好幾題就是這樣來的：同一個主題兩題並存，模型比對時猶豫，
結果兩邊都命不中，於是又轉人工、又被答一次、又多一題。

而且就算這次處理完了，**下次同樣的問法還是不會命中** —— 沒有任何東西被記下來。

## 做法

分兩件事：當下怎麼處理，以及下次怎麼命中。

### 當下：求助單直接給「用 #111 回覆」按鈕

開單訊息上就帶按鈕，同仁按一下就用題庫原文回客人：

```
📋 用 #111 支付管道異常（10003）是什麼意思？
📋 用 #44 請求頻率異常
📋 用 #22 商戶 ip 如何加白
```

不用打字、不用回後台翻、也不會新增任何題目。

候選從哪來：`ClaudeCodeMatcher` 的 schema 多回一個 `candidates` 陣列。
模型已經看過整份題庫，順手多回兩個候選幾乎沒有成本。

> ⚠️ **candidates 與 item_id 的判斷標準完全不同，prompt 要講清楚**：
> `item_id` 是要送給客人的，所以必須很確定；`candidates` 只給同仁看，
> 客人永遠不會收到，所以要**放寬標準**，沾得上邊就列進去。
> 尤其 `item_id` 填 null 的時候更要給 —— 那正是同仁最需要線索的時候。

按鈕上要帶題號與標題（截 24 字），同仁得先看得出那是哪一題才敢按。
模型可能挑到剛被停用或刪掉的題目，組按鈕時會 `findActiveItem()` 過濾掉。

### 下次：把客人那句原話記成問法樣本

同仁按下按鈕的同時，客人那句話就被記進 `quick_reply_phrasing`，
之後進 system prompt：

```
[id:111]（錯誤處理）
問題：支付管道異常（10003）是什麼意思？
客人也這樣問過：這是什麼錯誤呢／通道取不到是什麼意思／沒有通道可以用
答案：…
```

**這就是「關鍵字」，只是不是人工填的。**

題庫寫「回調」，客人說「錢沒進來」；題庫寫「10001」，客人說「簽名一直錯」。
那些字在 label 與 answer 裡都不會出現，模型只能靠語意猜。

不叫客服逐題填同義詞的三個理由：

1. **重複** —— `answer` 全文本來就整段進 prompt，「10003」「order_sn」模型早就看得到
2. **維護不起來** —— 一百多題要逐題填，之後每新增一題都要記得補，半年後脫節而且沒人會發現
3. **綁錯層級** —— 「錢沒進來」可能對到回調、也可能對到代收狀態，掛在單一題目上反而限制了它

從真實的沒命中案例累積，長出來的是客人真正用過的字，而且**越用越準**。

## 資料表

`quick_reply_phrasing`

| 欄位 | 說明 |
|---|---|
| `quick_reply_item_id` | cascadeOnDelete —— 樣本存在的唯一意義就是幫那一題被比對到 |
| `text` | 客人的原話 |
| `telegram_group_id` | nullOnDelete，回溯「誰在哪裡問的」用；群組刪了樣本仍有用 |
| `source` | 1=求助單按鈕, 2=後台手動新增 |

同一題已經有一模一樣的句子就不再存（`addPhrasing()` 先查 exists）——
客人手滑重複問、或兩個人問了同一句話，存第二筆只是讓 prompt 變長。

## 後台管理

**樣本沒有上限**（依需求決定），所以一定要看得到、清得掉：

- 題庫列表每題旁邊顯示 `💬 N`（0 筆時不顯示，大部分題目都是 0，每題掛個空標記只是雜訊）
- 點 `💬 N` 開「客人問過的說法」視窗，逐筆可刪
- 句數標記**不綁 `canEdit`** —— 只有檢視權限的人也該看得到累積了哪些說法

> ⚠️ **說法視窗刻意做成獨立 Modal，不塞進問答編輯視窗。**
> 塞進去的話刪一句就要再開一層確認 Modal，Bootstrap 疊兩層 backdrop
> 會把捲動鎖在錯的那一層。這裡的刪除改成**就地確認**（該列變成「確定刪除？」），
> 不會再開新的 Modal。

權限沿用既有的 `quick_reply.view` / `quick_reply.edit`，
permissionMap 不用動，也不用重跑 `SetPermissionSeeder`。

## 快取

問法樣本是 system prompt 的一部分，**新增與刪除都要清 `auto_reply.prompt.*`**，
否則要等 TTL（5 分鐘）才生效：

- 新增：`AutoReplySupportService::handleCandidatePicked()` 記完就清
- 刪除：`QuickReplyService::deletePhrasing()` 刪完就清

`QuickReplyService::flushMatchPrompt()` 為此從 private 改成 public。

> prompt 內容改了，cache key 跟著換成 `auto_reply.prompt.v3`。

## 順手做的重構

`AnswerSplitter`（長答案分則）從 `AutoReplyService` 抽成獨立類別 ——
現在有兩條送出路徑要用：自動回覆命中題庫，以及同仁按「用這題回覆」。
同一份答案不該因為是誰送的而排版不同。

## 注意事項

- 按了候選按鈕之後 ticket 進入 `REPLIED`，`isClosed()` 為真。
  同仁若又引用回覆作答，會收到「這張單已經處理過了」，不會重複回覆客人。
- `replyWithItem()` 中間那則送失敗時回傳的是 `$index > 0`（當作成功）——
  客人已經看到一部分，這時回報失敗會讓同仁重送一次而變成重複訊息。
- 求助單原本的 ①②③④ 按鈕流程沒有變動，兩組按鈕在不同訊息上並存。

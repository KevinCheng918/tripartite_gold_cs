# 任務卡異動通知（任務卡專區話題）

> 需求（2026-11-01）：「我有新增一個話題，他叫做任務卡專區，
> 如果有更動任務卡的話，要通知。」

**狀態：已實作（v3.54，2026-11-01）。**
**⚠ 兩件上線前置作業：①跑 migration ②到通知設定勾「任務卡專區」那個話題。**

| 題目 | 裁示 |
|---|---|
| 哪些事件 | 建立／狀態／指派人員／參與人／到期日／優先順序／專案站台／封存還原（**不含**標題、描述、打勾、留言、附件）|
| 連續異動 | **同一張卡幾分鐘內合併成一則** |
| 訊息內容 | 標題、專案、**專案負責人**、**指派人員**、變更前→後、**觸發者**（看過範例後調整：拿掉站台、加上兩個人員欄位、異動人改名）|
| 話題勾選 | 需求方自己勾 |

## 機制已經現成，加一個通知類型就接上了

內部支援群組的「逐話題勾選通知類型」那一套（見 [[support-group-topics]]）
已經在跑，而且擴充點很乾淨：

| 步驟 | 檔案 |
|---|---|
| 1. 註冊類型 | `config/constants.php` 的 `SUPPORT_TOPIC.TYPES` 加 `task_change` |
| 2. 顯示文字 | `resources/lang/{tw,cn,en}/notification.php` 的 `notice_type.task_change` ＋ `_hint` |
| 3. 設定頁 | **不用改** —— 類型是從 config 經 `settings.options.notice_types` 吐給前端的，加完就自己出現在每個話題的勾選清單裡 |
| 4. 發送 | `SupportGroupService::send($text, null, null, 'task_change')` |

⚠ `needs_reply` 填 **false**：這是單向通知，沒有人要引用回覆它 ——
填 true 會讓它「只能勾一個話題」，而這類通知勾幾個話題都無所謂。

⚠ **一個話題都沒勾時會發到主區**（那是這個設定頁一貫的行為，
`threadIdsFor()` 沒勾時回 `[null]`）。所以上線後請記得去把
「任務卡專區」那個話題的這一項勾起來，否則通知會跑到群組主區。

## ⚠ 真正的難題是「不要變成洗頻」

「更動任務卡」聽起來是一件事，實際上是**八個**進入點
（`TaskBoardService`）：

| 進入點 | 什麼時候發生 | 頻率 |
|---|---|---|
| `storeTask()` | 建立卡片 | 低 |
| `updateTask()` | 編輯視窗存檔、**面板的每一次 inline 編輯** | **高** |
| `moveTask()` | 拖曳換欄 | **高** |
| `archiveTask()` / `restoreTask()` | 封存／還原 | 低 |
| `updateChecklist()` | 描述裡打勾 | **極高**（已刻意不記活動紀錄）|
| `addComment()` / `updateComment()` / `deleteComment()` | 留言 | 中 |
| `deleteAttachment()` | 刪附件 | 低 |

### ⚠ 最容易被低估的一點：面板是**逐欄位**存檔的

詳情面板的 inline 編輯是 `saveField(fieldName, val)` → 一次打一支
`ajaxUpdateTask`。所以同仁整理一張卡片（改優先、換指派、補到期日）
**會連續觸發三次 `updateTask()`** —— 若每次都發一則，群組會被三則幾乎一樣的
訊息灌滿。

這跟「編輯視窗存檔」不同：那邊是一次送出全部欄位，`$changes` 自然就是一則。

### 所以「全部都發」不可行

`updateChecklist()` 更是明證 —— 它當初就是因為「每打一個勾記一筆會把活動紀錄
灌爆」才刻意不寫紀錄（見 [[task-board]]）。同一個理由適用於通知，而且更嚴重：
活動紀錄只是變長，群組訊息是會一直跳出來吵人的。

## 建議：只發「別人會想知道」的事件

| 事件 | 發不發 | 理由 |
|---|---|---|
| 建立卡片 | ✅ | 新工作進來了，是最該知道的 |
| 狀態變更（含拖曳）| ✅ | 卡片前進／退回是進度本身 |
| 指派人員變更 | ✅ | 直接影響「誰要做」 |
| 參與人變更 | ✅ | 同上，而且被加進去的人會想知道 |
| 到期日變更 | ✅ | 影響排程 |
| 封存／還原 | ✅ | 低頻但重要 |
| 優先順序變更 | ⬜ 建議發 | 低頻、而且會改變處理順序 |
| **標題變更** | ⬜ | 多半是訂正錯字 |
| **描述變更** | ❌ | 最頻繁，而且內容可能上萬字 |
| **勾選清單打勾** | ❌ | 極高頻，當初就刻意不記紀錄 |
| **留言** | ❌ 建議不發 | 留言本身就是在群組外的討論，而且有自己的未讀標記 |
| 專案／站台變更 | ⬜ | 低頻，發了也無害 |
| 附件刪除 | ❌ | 低頻但沒有人需要被通知 |

⚠ **不要做成「每個事件一個設定開關」** —— 那會變成設定頁上十幾個勾選框，
而使用者真正想要的只是「有動靜就讓我知道」。先用一組合理的預設，
真的吵再回來調。

## 訊息長什麼樣（定稿）

```
🔔 任務狀態更新通知

#12 主系統登入異常          ← 編號＋標題整串都是連結
指派：@MaryLee @JohnChang ｜ 負責人：@AmyWang
專案：三方金流 ｜ 到期：2026-11-05
優先序：🔴 緊急
狀態：進行中 → 測試中
新留言：1 則（張三）
觸發者：李小華
```

### ⚠ 指派人與負責人是 `@mention`

需求方 2026-11-01：「我要用標注的，這樣 Telegram 才會 @ 到。」

用 `TelegramUsernamePresenter::mentionLine()`，而人員資料走
`UserRepository::getNamesByIds()`。

⚠ **不要改用 `getMentionableByIds()`**：那支會濾掉工程、非正常狀態、
以及沒有 username 的人 —— 用在這裡會讓那些人從通知上**整個消失**，
而看訊息的人會以為「這張卡沒有指派人」。所以是撈全部的人，
再由 `mentionOrName()` 自己判斷：有 username 就 `@`，沒有就退回暱稱。

⚠ **多人之間用空白分隔，不要用「、」**：`@mary、@john` 會讓 Telegram 把
「、」當成 username 的一部分，兩個 `@` 都解析失敗。

⚠ **兩處 `select` 都要撈 `telegram_username`**
（`getNamesByIds()` 與 `Project::owner()`）——
少了它 `mentionOrName()` 會永遠退回暱稱，**而且不會報錯**，
看起來就像「這些人都沒設 Telegram」。

⚠ **`@` 只有在那個人也在這個群組裡才會真的推播。** 不在群組的話 Telegram
只會畫成藍字 —— 這不是程式能補的，要請那個人加入群組。

### 優先序：燈號 ＋ 自己一行

需求方 2026-11-01 指定格式 `優先序：🟡 中`，而且**排在狀態前面**。

| 優先序 | 燈號 |
|---|---|
| 低 | ⚫ |
| 中 | 🟡 |
| 高 | 🔴 |
| 緊急 | 🔴（沿用）|

⚠ 燈號在 `constants.TASK.CHANGE_NOTICE.PRIORITY_LIGHTS`，key 是
**常數名不是數字** —— 數字當 key 的話，優先序的值改了這裡會安靜地對不上。

⚠ **緊急沿用紅燈**：需求方只指定了低／中／高。高與緊急都是「紅色等級」，
而後面緊接著文字（`🔴 高` vs `🔴 緊急`）所以分得出來。
要給緊急獨立燈號就改那個 config。

這個版面是**看著實際產生的範例改了五輪**才定的（抬頭、站台、人員欄位的位置、
「」框、編號、連結全都動過）。每一項調整的理由：

⚠ **拿掉站台**：任務卡的站台常常是空的，而且看通知的人要的是
「這張卡是誰的事」，不是它掛在哪個站台。

⚠ **加上專案負責人與指派人員**：看到通知的第一個問題是「這要找誰」——
只有狀態變更的那種通知如果不帶這兩個，就得自己回看板查。

⚠ **「異動人」改叫「觸發者」**：跟「指派人員」放在同一則訊息裡時，
「異動人」會被讀成「負責處理的人」。指派人員是**這張卡該由誰做**，
觸發者是**這次是誰動的**，兩者常常不一樣。

⚠ **標題自己獨佔一行**，指派與負責人移到第二行：標題是連結，可點的範圍
只有那幾個字 —— 旁邊再接「指派：…」的話，使用者會以為整行都能點。

⚠ **標題不加「」框**：它已經是藍色帶底線的連結、而且自己一行，
一眼就看得出是標題，再加括號只是雜訊。

⚠ **編號放進連結裡面**（`#12 標題` 整串可點），不要擺在 `<a>` 外面 ——
點擊範圍大得多，擺外面使用者很容易點在編號上而沒反應。

### 版面是固定的，不做「有變更才出現」

前兩行是「這張卡現在長什麼樣」，第三段才是「這次改了什麼」。

所以到期日與優先順序**會同時出現在第二行（現狀）與第三段（變更）**——
這是刻意的：第二行回答「現在幾號到期」，第三段回答「剛剛被改成幾號」。
為了省一行而把現狀拿掉的話，每則訊息的行數就不固定，掃起來反而慢。

（中間試過「有變更就不印現狀」那一版，為此寫了一支 `hasLineFor()`；
改成固定版面之後那支就拿掉了。）

### ⚠ 專案負責人要多撈一個欄位，不然永遠顯示「未指派」

`Task::project()` 的 select 原本是 `['id', 'name', 'reactivated_at']` ——
**沒有 `owner_id`**，所以 `$task->project->owner` 會永遠是 null
**而且不會報錯**，訊息上就安靜地變成「未指派」。
（這個專案為「select 漏欄位」修過好幾次。）

⚠ 加的是 `owner_id` 一欄，**`owner` 關聯本身不在 `Task::project()` 上
eager load** —— 看板每張卡都走那個關聯，而看板不顯示負責人，載了是白撈。
由 `projectOwnerName()` 自己 `loadMissing('project.owner')`，
它一輪最多跑 `MAX_PER_RUN` 次。

⚠ `Project::owner()` 是 `withTrashed()` 的，所以負責人已離職時仍然查得到
名字。這裡**刻意不標「已離職」** —— 那是專案管理頁的事，
群組通知只要回答「這個專案歸誰」。

⚠ 指派人員用 `UserRepository::getNamesByIds()`：它不加任何狀態條件，
所以已停用或離職的人也顯示得出名字 —— 卡片還掛在他身上，寫「無」會更難追。

## 標題是連結：怎麼做到的，以及一條不能踩的線

看板現在會讀 `?task=3` 自動把那張卡的側邊面板打開
（`URLSearchParams` 解析，所以 `?a=1&task=3` 的順序也行；而且**不等
`loadBoard()` 回來** —— 面板走另一支 API，等它只會讓開卡變慢）。

⚠ **`<a>` 標籤可以直接送出去**，不必自己 escape：
`TelegramBotService::sendMessage()` 用的是 `parse_mode: HTML`，
而它的 `escapeHtml()` 轉義之後會把白名單內的標籤（含 `a`）還原回來。
自己先 escape 會變成雙重轉義，`&` 顯示成 `&amp;`。

### ⚠⚠ 網址裡絕對不能出現 `&`

`escapeHtml()` 還原標籤的 regex 是

```php
preg_replace('/&lt;(a)((?:\s[^&]*?)?)&gt;/i', '<$1$2>', $text)
```

屬性部分是 `[^&]*?` —— **不吃 `&`**。所以 `?task=3&from=tg` 這種網址會讓
整個 `<a>` **還原失敗**，群組裡收到的是
`&lt;a href="..."&gt;標題</a>` 這樣的可見亂碼。

2026-11-01 實測四種情況確認：

| 情況 | 結果 |
|---|---|
| `?task=3` | ✅ 連結正常 |
| `?task=3&from=tg` | ❌ **`<a>` 還原失敗，變成可見亂碼** |
| 標題含 `&`（「A&B 對帳」）| ✅ 正確轉義、連結正常 |
| 標題含 `<`（「a\<b 異常」）| ✅ 正確轉義、連結正常 |

> 要加第二個查詢參數的話，**得先改 `escapeHtml()` 的 regex**，
> 不要在 `titleLink()` 裡硬塞 —— 而且本機測不出來（本機不會真的發 Telegram）。

⚠ **`APP_URL` 一定要是對外的網址**：排程在 console 跑，`route()` 只能靠
`config('app.url')`，沒有「目前的網域」可以推斷。設成 localhost 的話
群組裡的連結點了打不開。（dev 目前就是 localhost，正式環境已確認正確。）

## 卡片編號

編號同時顯示在三個地方：通知訊息（連結文字）、**看板卡片**（專案 badge
旁邊的灰色小字）、**側邊面板**（標題上方）。

⚠ 後兩個是必要的：群組裡寫「#12」，看板上沒有的話對不起來。

⚠ 面板的編號**擺在標題外面**，不要塞進 `.field-value` —— 那一格的
innerHTML 會被原樣存回 `title`，編號會被寫進卡片名稱裡
（描述的進度文字當初就是為同一個原因擺在標題旁邊）。

⚠ **一次存檔只發一則，列出該次所有變更欄位**（`$changes` 本來就是這個形狀）。

⚠ **描述的變更只寫「描述已更新」，不要帶內容** —— 規章那次就踩過
「上萬字塞進 Telegram 單則訊息會整則發不出去」（見
[[2026-10-30-telegram-chunk-utf16]]）。而且描述是 HTML，貼進 Telegram 是亂碼。

⚠ **沒有卡片深連結可用**：看板目前不支援 `?task=3` 之類的網址開特定卡片，
所以訊息裡放不了「點這裡打開」。要做得先讓看板讀 query string ——
那是另一個題目，這次先不做。

## ⚠ 實作時一定要注意的三件事

### 1. 通知失敗不能讓操作失敗

照 `ajaxTopupStore()` 的既有做法：通知**擺在資料寫進去之後**，而且整段
try/catch 吞掉例外只記 log。

> 通知沒送到頂多大家晚點才知道，但卡片存檔被通知的例外中斷的話，
> 同仁會以為沒存到而重複操作。

### 2. ⚠ `狀態` 在 `changes` 裡**必須保持整數**

`TaskQueryCommandService::recentlyResolvedTaskIds()` 會讀
`Arr::get($activity->changes, '狀態.to')` 並跟
`constants.TASK.STATUS.RESOLVED` 比對。

如果哪天有人「順手」把 `activityValue()` 的 `status` 也翻成「已解決」這種
顯示文字，那支指令會**安靜地永遠回空陣列** ——「查卡片進度」就再也查不到
近期完成的卡片，而且不會報錯。

（2026-10-31 驗證過目前仍是整數，沒有壞。）

### 3. 發送要走 Service，不要寫在 Controller

通知內容的組裝是商業邏輯 —— 照 `FinanceNoticeService`／`ShiftNoticeService`
的樣子開一支 `TaskChangeNoticeService`，`TaskBoardService` 呼叫它。

⚠ **不要塞進既有的 `TaskNoticeService`**：那一支是「每天早上私訊自己的卡片」
（走 `StaffDmService`），跟這次的群組通知是不同的收件人與不同的觸發方式，
混在一起之後很難看出哪個方法是給誰的。

## 明確不做

- **不做每個事件各自的開關**（理由見上）
- **不做卡片深連結**（看板還不支援，是另一個題目）
- **不通知描述與勾選清單的變更**（頻率太高）
- **不排除「自己改的」** —— 這是群組通知不是私訊，沒有「收件人」可以比對；
  訊息裡會標出異動人，看到是自己改的自然會略過

## 實作：合併怎麼做的

需求方選了「合併」，而這是整個功能唯一有技術難度的地方。

### ⚠ 不能用 delayed queue

這個專案的 `QUEUE_CONNECTION` 是 **`sync`**（見 `.env`）——
延遲派送根本不會生效，任務會當場同步執行，等於沒有合併。

所以走**排程指令**（`task:notify-changes`，`everyMinute`），
那也是這個專案既有的做法（已經有七八支 `everyMinute` 的指令）。

### ⚠ 不開新的緩衝表，重用 `task_activity`

要合併就得先把「還沒通知的異動」存下來，而 `task_activity` 本來就一筆一筆
記著誰在什麼時候改了什麼 —— **只差一個「發過了沒」的標記**。
所以只加一欄 `notified_at`（nullable timestamp ＋ 索引）。

另開一張表等於把同一份資料記兩遍，而兩份遲早會不一致。

⚠ **索引要含 `notified_at`**：排程每分鐘問一次「有哪些還沒處理的」，
沒索引就是每分鐘全表掃一次，而那張表只會越來越大。

### ⚠ migration 一定要把既有紀錄標成「已處理」

```php
DB::table('task_activity')->whereNull('notified_at')
    ->update(['notified_at' => DB::raw('`created_at`')]);
```

不標的話，排程第一次跑就會把資料庫裡**所有歷史異動**當成「還沒通知」，
一次把幾百則舊訊息灌進群組 —— 那是上線當下最糟的事。

用 `created_at` 而不是 `now()`：看紀錄的人才分得出「這筆是補標的歷史資料」。

### 流程

```
異動發生 → logActivity() 照舊寫 task_activity（notified_at = null）
   ↓
排程每分鐘：撈 notified_at IS NULL，依 task_id 分組
   ↓
這張卡最後一筆異動還在窗口內？ → 繼續等（合併窗口會一直往後推）
   ↓ 安靜滿 3 分鐘
把這張卡累積的異動併成一則發出去 → 標記全部 notified_at
```

### ⚠ 六個實作細節

**1. 同一個欄位被改好幾次只輸出一行** —— 取**第一筆的 from** 與
**最後一筆的 to**。不合的話「待處理→進行中、進行中→審核中」會變兩行，
而看的人只想知道「從待處理變成審核中」。改來改去又改回原值則整行不報。

**2. 沒有要通知的內容時照樣要標記** —— 只改了描述或標題的那些異動，
不標的話排程每分鐘都會再撈到同一批，永遠掃不完。

**3. 發送失敗也標記。** 留著 null 聽起來像「下次重試」，但 Telegram 的失敗
多半是設定問題（話題被刪、Bot 被踢），不會自己好 ——
結果是每分鐘重試一次直到有人發現。寧可漏一則，也不要讓排程卡在同一張卡上。

**4. 群組沒設定時在最前面短路，而且不標記。** 設定補上之後，
這段期間的異動應該還是要發得出去。

**5. 單次有上限（`MAX_PER_RUN`）。** 排程停過一陣子（主機重開、指令掛掉）
之後累積的卡片會一次湧出來，沒有上限就是幾百則訊息同時打進 Telegram ——
直接撞上 API 速率限制。沒處理完的留到下一分鐘。

**6. 排程一定要 `everyMinute` ＋ `withoutOverlapping`。**
前者因為排程間隔會疊加在合併窗口上（每五分鐘跑的話，3 分鐘窗口實際會變
最多 8 分鐘）；後者因為 `notified_at` 是**發完才標**的，
上一輪還在發就再跑一次會把同一批撈兩次，群組收到兩則。

### ⚠ 狀態與優先順序要在「組訊息」時才翻成文字

`changes` 裡它們是**數字** —— `TaskBoardService::activityValue()` 刻意不翻，
因為 `TaskQueryCommandService::recentlyResolvedTaskIds()` 要拿
`Arr::get($changes, '狀態.to')` 跟 `constants.TASK.STATUS.RESOLVED` 比對。

> 哪天有人「順手」把 status 也翻成「已解決」這種顯示文字，
> 那支指令會**安靜地永遠回空陣列**，「查卡片進度」就再也查不到近期完成的
> 卡片，而且不會報錯。

（2026-10-31 驗證過目前仍是整數。）

所以翻譯放在 `TaskChangeNoticeService::readable()`，而且狀態／優先的
數字→語系 key 是**從 config 反查**，不寫死 `[1 => 'pending', …]` ——
狀態常數加一個就得記得回來改，漏改只會讓訊息顯示成原始數字。

⚠ 指派人員與參與人**已經是名字陣列**（寫入時就翻好了），
`readable()` 只負責把陣列接成一行。

### ⚠ `FIELD_LABELS` 改成 public

通知服務要把 `constants.TASK.CHANGE_NOTICE.FIELDS` 那幾個**欄位名**換成
`changes` 裡的**中文 key**，所以要讀 `TaskBoardService::FIELD_LABELS`。

在通知服務裡自己抄一份的話，改了標籤就會對不上 —— 而結果是安靜地不通知。

## 裁示紀錄（2026-11-01）

### 1. 哪些事件要通知？

- (a) **建立／狀態／指派人員／參與人／到期日／優先順序／專案／站台／封存還原**
  （不含標題、描述、勾選清單、留言、附件）（**建議**）
- (b) 再加上**標題**與**留言**
- (c) 只發**建立**與**狀態變更**兩種（最安靜）

### 2. 面板逐欄位存檔造成的連續通知，要處理嗎？

- (a) **不處理** —— 一次改一個欄位就是一則。最單純，也最即時（**建議**）
- (b) **同一張卡 N 分鐘內合併成一則**（需要暫存狀態，而且通知會延遲 N 分鐘）
- (c) 改成「面板的 inline 編輯不通知，只有編輯視窗存檔才通知」
  （少了最常用的那條路，等於大部分異動都不會通知）

### 3. 留言要不要通知？

- (a) **不要**（**建議**）—— 留言有自己的未讀標記，而且討論搬到群組會變兩邊都在講
- (b) 要，但只通知「新增留言」不通知編輯／刪除

### 4. 卡片標題之外還要帶什麼？

- (a) **專案、站台、異動欄位（前→後）、異動人**（**建議**）
- (b) 再加上**目前的指派人員**（讓看到的人知道該找誰）
- (c) 只有標題與異動欄位（最精簡）

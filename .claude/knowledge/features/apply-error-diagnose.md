# 客人貼開單 request，幫他找出錯在哪一欄

> 需求（2026-10-21）：「我 Telegram 對話這邊，客人有時候會直接貼開單 request，
> 要能夠根據他的資訊找到錯誤…客人問說，為什麼是 -1 訂單異常，這時候要去找他
> 欄位的規則限制，例如：order_sn 長度要是 10~50，去確認錯誤原因」
>
> 補充：
> - 「他這個很明顯是其中欄位問題，可以先預排查」
> - 「那坨是客人貼過來的」
> - 「只需要跟客人說，資料哪邊錯就好，不要提到資料庫多少什麼的機敏資訊」
> - 「『看起來應該是 6823，麻煩改填這個』這段聽起來像是我們的系統問題，但明明
>   是對方的錯，應該要回文件上寫的長度是多少，然後範例是什麼」
>
> 決定（問過需求方）：**找到明確原因就直接回客人，查不出來只給客服看**。

## ⚠ 為什麼 `-1` 是欄位問題，但比對驗證規則找不到

我第一版的判斷錯了，記下來免得再犯。

主系統的錯誤碼是這樣分的：

| 碼 | 來源 |
|---|---|
| `10001`–`10008` | 中介層與 `ApiErrorException`（加簽、授權、支付異常…） |
| `-2` ~ `-19` | **欄位驗證失敗，每一種各有專屬碼** |
| **`-1`** | `PaymentController` **最外層的 `catch (\Exception)`** |

所以「`-1` 不可能是 Laravel 驗證失敗」是對的 —— 但我就此推論「那就不是欄位
問題」，**那一步錯了**。

真正的 `-1` 來源是**驗證放行、但寫不進資料庫**的那段落差：

```
bank_branch_code   驗證 max:15    欄位 varchar(10)
                   ↑ 11~15 字過得了驗證，INSERT 時爆掉
                     拋的是 PDO 例外不是 ApiErrorException → 掉進最外層 catch → -1
```

需求方給的實例正是這一種：`bank_branch_code` 填了
`台北富邦鼓山分行(6823)` 共 **14 字**（正確值是 `6823`）。

**一般化：驗證規則與資料庫定義是兩套，兩套之間的落差就是「不會報錯只會噴通用
錯誤」的區間。** 只掃其中一套，等於看不見這一整類問題。

### 落差清單（`config/apply_rules.php` 的 `max` vs `db`）

| 欄位 | 驗證 | 資料庫 | 會變 `-1` 的區間 |
|---|---|---|---|
| `bank_branch_code`（代付） | `max:15` | `varchar(10)` | **11~15 字** |
| `user_name` | **沒驗長度** | `varchar(50)` | > 50 字 |
| `user_id_number` | **沒驗長度** | `varchar(20)` | > 20 字 |
| `user_birthday` | **沒驗格式** | `date` | 不是日期格式 |
| `client_ip` | 沒驗 | `varchar(50)` | > 50 字 |
| `notify_url`／`note` | 沒驗 | `varchar(255)` | > 255 字 |
| 代收的 `email`／`address` | 沒驗 | `varchar(255)` | > 255 字 |

## 三種判定，意義完全不同

| 分類 | 意思 | 會不會跟客人講 |
|---|---|---|
| `blocked` | 違反驗證規則 → API 回**該欄位的專屬碼** | 只講對得上那個碼的 |
| `fatal` | 過驗證但超過資料庫上限 → **這才是 `-1` 的原因** | 會講 |
| `suspicious` | 都合規，但內容看起來放錯（分行代碼填了名稱） | **不講**（那是猜的） |

## ⚠ 對客人一律引「文件上寫的」規格與範例

需求方 2026-10-21，兩條合起來看：
1. 「只需要跟客人說，資料哪邊錯就好，不要提到資料庫多少什麼的機敏資訊」
2. 「『看起來應該是 6823，麻煩改填這個』這段聽起來像是我們的系統問題，
   但明明是對方的錯，應該要回文件上寫的長度是多少，然後範例是什麼」

第一版寫成「看起來應該是 6823，麻煩改填這個」——**兩個問題**：
像是我們在幫他猜，而且顯得是我們系統有毛病。
實際上他違反的是**文件規格**（商戶 API 文件寫得清清楚楚），
照文件講才站得住腳。

**同一個欄位有三個數字，而文件才是雙方的合約：**

| | 文件 | Laravel | 資料庫 |
|---|---|---|---|
| `bank_branch_code` | **10** | 15 | 10 |

文件寫 10、資料庫也是 10 —— 中間那個 `max:15` 才是異常值。

所以規則表多存一層 `doc_max`／`doc_hint`／`doc_example`（來源：
主專案 `resources/views/docs/master.blade.php`，代收段與代付段各一份表），
**跟客人講的數字一律取 `doc_*`**：

| 情況 | 對客 | 對內 |
|---|---|---|
| 分行代碼 14 碼 | 「文件規格上限 **10** 碼，您這筆是 14 碼。範例：`0015`」 | 「14 字，欄位只收 10 字 → 寫入失敗」 |
| 訂單號用了 `-` | 「文件規格是『長度 10~50，只能用英文、數字、下底線(_)』，範例：`AD1234567890`」 | 「格式不符，會回 -3」 |
| 生日格式錯 | 「文件規格是『日期格式 Y-m-d』，範例：`1990-03-15`」 | 「值是『民國80年3月』，不是日期格式」 |
| **姓名 60 碼**（文件沒寫上限） | 「您這筆是 60 碼，長度超過系統可接受的範圍」 | 「60 字，欄位只收 50 字」 |
| 下一步 | （不提） | 「請工程查主系統 payment_error log，搜這個 order_sn」 |

⚠ **文件沒寫上限的欄位就退成不帶數字的說法**（`too_long`）——
寧可講得籠統，也不要把內部的欄位長度交出去。`user_name`、
`user_id_number`、`client_ip`、`notify_url` 都是這一類（文件完全沒提長度）。

## ⚠ 只講「對得上那個錯誤碼」的那幾條

主系統的驗證**只回第一個錯誤**（`$validator->errors()->first()`）。
所以客人收到的碼只對應到一欄 —— 其他「違規」很可能只是他**沒貼完整**
（只貼了前幾個參數）。照單全報會變成叫他補一堆其實有帶的欄位。

規則：

- 碼是某一欄的專屬碼 → 只講對得上那個碼的
- 碼是通用碼（`-1`） → 只講 `fatal`
- 沒有碼 → 盡力而為，`fatal` 與 `blocked` 都講

⚠ 內部文案會多一句「已經跟客人講的只有對得上錯誤碼的那幾條」——
不然同仁看到內部列了四條、客人只收到一條，會以為訊息漏送。

## 判不出代收還是代付時

請求網址被截掉時兩套規則都跑，**挑「能解釋客人收到的那個碼」的那一套**，
違規少的只是退而求其次。

⚠ 只看「違規少」會挑錯：訂單號 `abc-def-ghij` 在代收規則下完全合規（代收允許
`-`），於是挑了代收並回「欄位都正常」—— 但客人收到的是 `-3` 訂單號格式異常，
那正是代付規則擋下來的（代付只允許 `_`）。**能對上碼的那一套才是真相。**

⚠ 代收與代付的 `order_sn` 正則不一樣（代收 `-`、代付 `_`），而兩邊都回 `-3`，
看錯誤碼看不出差別 —— 這是最容易被忽略的一條。

## 接在哪裡

`AutoReplyService::handle()` 裡，**擋在題庫比對之前**：

```
客人訊息 → 合併這一輪 → 取脈絡
  → 【開單預排查】 ← 新增，像開單紀錄就處理掉
  → 題庫比對 → 命中就答 / 轉人工
```

⚠ 擺在題庫前面的理由：題庫裡不會有「一整坨 print_r」這一題，現在的結果一定是
轉人工；而且那坨很長，拿去比對只是把額度燒在一個必然答不出來的問題上。

⚠ **「我還是最後一則嗎」這一道要自己做一次**（`hasNewerInbound()`）：
解析也要跑幾秒，客人很容易在那期間又補一句。少了它，連著貼兩則會被回兩次 ——
跟題庫那條路同一個坑。

查不出原因時走原本的 `replyWait()`（轉人工），把診斷塞進求助單的 hint。
為此 `replyWait()` 與 `buildHint()` 各多一個 `$extraHint` 參數。

⚠ `buildHint()` 原本 `blank($result)` 就 early return —— 開單預排查走的正是
「沒有比對結果、但有診斷要給同仁」這條路，不改的話整份診斷會被丟掉。

## 形狀粗篩可以用關鍵字

`looksLikeDump()` 用 `order_sn`、`/api/withdraw`、`原始參數` 這類特徵字，
命中 2 個以上才送模型。

⚠ 這跟 2026-10-13 拿掉指令粗篩**不衝突**：那邊篩的是**人**講的話
（講法永遠追不完），這裡篩的是**機器**印出來的 dump（`print_r` 格式固定）。
而且漏接只是退回原本的轉人工，不是默默出錯。

## 模型只解析，規則一律查設定檔

跟排程設定那支同一個分工：模型把那坨文字變成「欄位 => 值」與 `code`／`msg`，
**長度與規則一律查 `config('apply_rules')`**。

⚠ 讓模型自己判斷「order_sn 應該幾碼」，它會編一個很合理的數字出來，
而客服會照著回客人。

⚠ 值要**原文照抄**：長度判斷是整個診斷的核心（11 字跟 10 字差一個 `-1`），
模型「順手整理一下」就全毀。

⚠ `agent` 與 `sign` 不收進 fields —— 不是要診斷的欄位，而 `sign` 是敏感資訊。

## 踩到的坑

⚠ **`blank(strtotime($value))` 永遠不成立**：`strtotime()` 失敗回 `false`，
而 `blank(false)` 回的是 **false**（`blank()` 對布林一律回 false）。
所以生日填「民國80年3月」會被當成正常 —— 而它正是 `-1` 的原因之一。
改成 `strtotime($value) === false`。同一個坑第三次踩，見
[[2026-10-12-filled-on-boolean]]。

## 各通道額外要求的欄位

`config('apply_rules.CHANNEL_REQUIRED')` 記了 47 組（通道 × 代收／代付），
來源是 `Apollo::verifyParamsRequired()`。

⚠ 沒填的話回的是**各自的專屬碼**（`-9`／`-10`／`-12`…），**不是 `-1`** ——
掃過 47 組沒有一組會掉進 `-1`。所以這份表的用途是「告訴客人這個通道還要帶
什麼」，不是用來解釋 `-1`。

⚠ **客服系統不知道某個站台用哪個通道**（那在主系統的 `payment` 表），
所以目前只是參考資料，程式還沒拿它做判定。

## 驗證

**真實案例端到端**（真的呼叫模型解析那坨）：抓出 `bank_branch_code` 14 字 >
欄位 10 字 → 對客回「看起來應該是『6823』」、對內回「14 字，欄位只收 10 字」。

**七種情境**：欄位全合規 ＋ `-1`（不回客人、轉人工附診斷）／代付訂單號用了 `-`
（回 `-3`）／必填沒帶（`-7`）／分行代碼填名稱但長度過得去（可疑、不斷定）／
判不出代收代付（挑能對上碼的那一套）／生日格式壞掉（`-1` 的來源）／
一般客人問句（粗篩就回 false）。

## 待釐清

- 規則表是**快照**（三層：文件／驗證／資料庫），主專案改了任何一層這邊都不會
  知道，要重掃。
  ⚠ 這份比 `apollo_fields` 更危險：那邊過期是「少列欄位」，這邊過期會變成
  **對客人講錯的文件規格**。
- ⚠ **`bank_branch_code` 的 `max:15` 在主專案是個真的 bug**：文件寫 10、
  欄位 10，驗證卻放到 15。對齊之後客人至少會收到 `-18`（分行代碼格式異常）
  而不是看不懂的 `-1`。這一條值得請工程修 —— 修好之後這支診斷的
  `fatal` 那一區就幾乎不會有東西了（而那是好事）。
- `amount` 的上下限是該商戶在主系統的設定，客服系統查不到 —— 目前只驗格式，
  **絕對不要猜一個範圍**。
- `CHANNEL_REQUIRED` 還沒用上（需要知道站台用哪個通道）。

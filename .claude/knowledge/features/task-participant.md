# 任務「參與人」欄位與搜尋列改版

> 需求（2026-10-30）：「任務版要新增一個欄位是參與人，在總覽時不用看到，
> 但點進去卡片詳細內容時要能夠看到跟編輯。上面的搜尋列，我要能搜尋有參與的
> 卡片或是指派人是我的卡片。目前上方搜尋列有點醜，可以參考內勤管理做重新排版。」

**狀態：規劃中，尚未實作。待裁示四題（見文末）。**

## 先把語意定下來，不然這個欄位會沒有人知道該填誰

任務已經有「指派人員」（`assignee_ids`）了，再加一個「參與人」——
**兩者的差別必須講得出來**，否則兩個欄位會被隨意互換使用，
三個月後沒有人知道該看哪一個。

| 欄位 | 意思 | 誰該被填進去 |
|---|---|---|
| **指派人員**（`assignee_ids`）| **負責把這件事做完的人** | 這張卡片結案與否由他負責 |
| **參與人**（`participant_ids`）| **一起處理或需要知道的人**，但不負責結案 | 幫忙查過的人、被諮詢的人、要跟進結果的人 |

⚠ 建議在畫面上用一句話標出來（`field_participant_hint`），
不然使用者只會看到兩個長得一樣的人員欄位。

## 資料結構：照 `assignee_ids` 的樣子

```
task.participant_ids   JSON nullable   參與人（不負責結案；可以多人）
```

⚠ **刻意不開關聯表**，跟 `assignee_ids` 一致 —— 這個系統的任務參與者不需要
「加入時間」「角色」之類的額外欄位，開表只會多一層 join。

⚠ **`whereJsonContains` 要同時比整數與字串**：`assignee_ids` 那邊已經踩過了
（`TaskRepository::getBoard()` 現在是
`orWhereJsonContains('assignee_ids', $id)->orWhereJsonContains('assignee_ids', (string) $id)`）——
前端送上來的可能是 `["3"]`，只用整數比就全部對不上，而且**不會報錯、
只會搜不到**。新欄位必須照抄這個雙重比對。

⚠ **nullable**：既有的任務全部沒有參與人，預設就是空的。

## 畫面一：詳細內容（側邊面板）

需求方：「總覽時不用看到，但點進去卡片詳細內容時要能夠看到跟編輯。」

面板上方那塊虛線框的屬性區現在是 `row g-1`：

```
專案(3)  站台(3)  指派人員(6)
狀態(3)  優先(3)  到期日(6)
```

參與人插在**指派人員的下一行**，兩個人員欄位上下相鄰才看得出差別：

```
專案(3)  站台(3)  指派人員(6)
參與人(6)          到期日(6)        ← 參與人佔 6，狀態與優先往下
狀態(3)  優先(3)
```

⚠ 編輯方式**照抄 `assignee_ids` 那一套**（`js-prop-edit` ＋ 行內勾選清單，
見 blade 第 1158 行附近），不要另外做一個 modal ——
同一種操作兩種介面，使用者會以為它們是不同的東西。

⚠ **總覽卡片一行都不要加**（需求明講）。卡片上現在已經有專案、站台、
指派人員、到期日、優先順序 —— 再塞一排人名會讓卡片變成兩倍高，
而看板的價值就是一眼掃完。

## 畫面二：搜尋列改版（照內勤管理）

現在是**一整排**用 `|` 隔開的控制項，全部擠在一行：

```
篩選 [全部專案][全部人員][全部優先] | 排序 [建立時間][新→舊] | [搜尋標題][搜尋] | ☐僅顯示已過期
```

難看的原因不是樣式，是**沒有分組也沒有標籤** —— 七個控制項並排，
每一個都要點開才知道是什麼。

內勤管理（`staff-manage`）的做法是：

- 一張 `main-card`，`card-header` 右邊一個「收合」連結（`data-bs-toggle="collapse"`）
- `row g-3` 網格，每格 `col-md-3 col-6`
- 每格都是 `<label class="form-label fw-bold">名稱：</label>` ＋ 控制項
- 最後一列右對齊的「重設」＋「搜尋」兩顆鈕

改成：

```
┌─ 篩選 ───────────────────────────────── 收合 ─┐
│ 專案：[全部專案]  人員：[全部人員]  優先：[全部優先]  關鍵字：[搜尋標題] │
│ 排序：[建立時間][新→舊]   與我相關：[☐我參與的 ☐指派給我的]  ☐僅顯示已過期 │
│                                      [重設] [搜尋] │
└──────────────────────────────────────────┘
```

⚠ **「收合」要記住狀態**（`localStorage`）：看板是每天盯著的頁面，
每次進來都要再收一次會很煩。`staff-manage` 目前沒做這件事，
但那一頁不是每天開著的。

⚠ **「搜尋」鈕要留著**，不要改成「改一個就自動查」：關鍵字是打字的，
每打一個字送一次請求等於把 `ajax-board` 當搜尋建議用（那支會撈五欄全部卡片）。

## 搜尋「與我相關」

需求方：「我要能搜尋有參與的卡片或是指派人是我的卡片。」

**建議做兩個獨立的勾選框，可以同時勾**：

| 勾選 | 條件 |
|---|---|
| ☐ 我參與的 | `participant_ids` 含我 |
| ☐ 指派給我的 | `assignee_id` 是我 **或** `assignee_ids` 含我 |
| 兩個都勾 | 上面兩者**取聯集**（`OR`）—— 「跟我有關的全部」 |

⚠ **兩個都勾要 OR 不是 AND**：需求的原文是「有參與的卡片**或**指派人是我的
卡片」。做成 AND 的話，只會列出「既是參與人又是指派人」的卡片 ——
那是極少數，使用者會以為篩選壞了。

⚠ 這兩個條件要包在**同一個 `where(function ...)`** 裡，不能散著加：

```php
// ⚠ 散著加會變成「AND participant AND assignee」，兩個都勾就什麼都搜不到
$query->where(function ($q) use ($userId, $mine, $participating) { ... });
```

⚠ **既有的「全部人員」下拉維持原樣**（只篩指派人員），不要順手讓它也比對
參與人 —— 那個下拉的語意是「這個人負責哪些卡片」，混進參與人之後
「某人手上有幾張卡」就算不準了。「與我相關」是另一個問題，用新的控制項。

## 異動紀錄

參與人變更**要記**，而且已經有現成的機制 —— 2026-10-30 剛把
`TaskBoardService` 的 `FIELD_LABELS` 收成常數、`activityValue()` 負責把 id
換成名字（見 [[2026-10-30-task-activity-raw-values]]）。

所以只要：

1. `FIELD_LABELS` 加 `'participant_ids' => '參與人'`
2. `activityValue()` 的 `assignee_ids` 那個分支改成同時認 `participant_ids`

⚠ 不要為參與人另寫一套翻譯 —— 它跟指派人員的形狀一模一樣（id 陣列 → 名字）。

## 權限

⚠ **不開新 keyword**，沿用 `task_board.update`：這跟改指派人員是同一件事
（決定誰碰這張卡片），而且現有的屬性編輯全部走它。
再切一個 keyword 只會讓權限頁多一列沒有人知道差別的東西。

| 檔案 | 說明 |

| `app/Models/Task.php` | `$casts` 加 `'participant_ids' => 'array'`；`$fillable` |
| `app/Repositories/TaskRepository.php` | `LIST_COLUMNS`／`DETAIL_COLUMNS` 加 `participant_ids`；`getBoard()` 加「與我相關」的條件 |
| `app/Services/TaskBoardService.php` | `FIELD_LABELS` 加參與人；`activityValue()` 認 `participant_ids`；`storeTask()`／`updateTask()` 收這個欄位 |
| `app/Http/Requests/TaskBoard/*` | 新增與更新都加 `participant_ids` 的驗證（`sometimes|nullable|array`）|
| `app/Http/Resources/TaskResource.php` | 加 `participant_ids` 與 `participants`（照 `assignees` 的 `$userCache` 做法，**不要逐筆查**）|
| `app/Http/Controllers/Admin/TaskBoardController.php` | `ajaxBoard()` 收兩個新篩選參數 |
| `resources/views/admin/task-board/index.blade.php` | 搜尋列整個換成 staff-manage 的版型；面板屬性區加參與人；新增視窗加參與人勾選 |
| `resources/lang/{tw,cn,en}/task_board.php` | 參與人、提示、兩個篩選、重設⋯⋯三語系 |
| `config/changelog.php` | 版本紀錄 |

⚠ `TaskResource` 已經有一個 `self::$userCache` 在處理 `assignees`
（避免每張卡片都查一次使用者）—— 參與人**一定要共用那個 cache**，
不然一頁幾十張卡片就是幾十趟查詢。

⚠ **`LIST_COLUMNS` 漏加 `participant_ids` 的話**，看板上的卡片
（包括前端要用的篩選判斷）取不到值，而且**不會報錯** ——
這個專案為「select 漏欄位」修過好幾次。

## 明確不做

- **不在總覽卡片顯示參與人**（需求明講）
- **不做「參與人也能編輯這張卡片」** —— 參與人是個資訊欄位，不是權限
- **不通知被加為參與人的人**（沒有這個需求；真要的話接 `StaffDmService`）
- **不順手把這一頁的 JS 搬到 `public/js`** —— 2000 多行，獨立重構

## 待裁示

### 1. 「與我相關」的呈現

- (a) **兩個獨立勾選框**（我參與的／指派給我的），可同時勾，兩個都勾取聯集（**建議**）
- (b) 一個下拉：不限／我參與的／指派給我的／跟我有關的全部
- (c) 一顆「只看我的」按鈕，涵蓋參與＋指派（最簡單，但分不開兩種）

### 2. 搜尋列要不要可收合

- (a) **可收合，而且記住狀態**（**建議**：看板是每天盯的頁面）
- (b) 可收合但不記狀態（跟 staff-manage 完全一致）
- (c) 不收合，就是一張固定的篩選卡

### 3. 參與人在面板上的位置

- (a) **指派人員的下一行，佔半排**（**建議**：兩個人員欄位相鄰才看得出差別）
- (b) 跟指派人員並排（各佔 3）—— 比較省空間，但兩欄會很窄，人多就被截斷
- (c) 放在屬性區外面、描述上方獨立一列

### 4. 新增任務時要不要就能填參與人

- (a) **要**（新增視窗已經有指派人員的勾選清單，照抄一份）
- (b) 不要，新增完到面板再加（新增視窗已經很長了）

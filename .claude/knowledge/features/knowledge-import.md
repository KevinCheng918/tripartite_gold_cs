# 主系統知識題庫（QuickReplyKnowledgeSeeder）

> **狀態：已完成實作，待執行 migration 與 seeder。**

## 目標

主系統（`tripartite_gold`）的錯誤碼、狀態碼、API 欄位規則只存在於程式碼裡，
客人一問就得轉人工。把這些寫進題庫，自動回覆就答得出來。

## 為什麼值得做

實際遇到的案例：客人貼了一整串代付 API log 問「這筆是不是 error520」。
答案其實就在主系統的 `config/constants.php` —— 回調 `status: '02'`
對代付來說是 `WITHDRAW_STATUS.FAIL`（失敗）。但題庫沒有，只能轉人工。

而且整理的過程挖出兩個**程式碼裡才看得到的坑**，客服與商戶都會踩：

### 坑 1：同一個 `02`，代收是成功、代付是失敗

| 狀態碼 | 代收 | 代付 |
|--------|------|------|
| `00` | 待付款 | 待付款 |
| `01` | 成功 | 成功 |
| `02` | **群組單成功** | **失敗** |
| `03` | 失敗 | — |

### 坑 2：商戶訂單號的規則，代收與代付不一樣

| | 允許的字元 |
|---|---|
| 代收 | `^[A-Za-z0-9\-]{10,50}$` → **連字號** `-` |
| 代付 | `^[A-Za-z0-9\_]{10,50}$` → **底線** `_` |

商戶代收用 `abc-123` 沒問題，代付照用就被擋。
而代付的錯誤訊息只寫「商戶訂單號格式異常」，完全沒提這件事。

## 做法：seeder，不是匯入指令

一開始做成 `quick-reply:import` 指令去讀主系統的檔案，後來改成 seeder。

改的理由：

- **不必耦合主系統的檔案結構**。主系統搬個目錄、改個陣列名就會壞
- **避開 `env()` 的坑**。主系統的 `constants.php` 用了 `env()`，
  在客服系統裡 `require` 會讀到**客服系統的 `.env`** —— 目前只取寫死的狀態碼所以沒事，
  但擴充到 `OPEN_SETTING` 那類環境相關設定就會拿到錯的值
- **未來只要維護一個檔案**

代價是主系統改了錯誤碼不會自動同步，要人工回來改這份 seeder。
seeder 的類別註解裡記了每一題的出處，方便回頭核對。

## 重跑安全

**已經建過的題目完全不動。** 客服一定會再潤飾語氣（題庫答案是原文送給客戶的），
重跑 seeder 不該把人的修改洗掉。

判斷靠 `quick_reply_item.import_key`，**不是比對問題文字** ——
客服改過題目文字之後，比對文字會再插一筆重複的進去。

停用中的題目也算「已建過」：客服把某題停用是刻意的，不該又冒出來一筆。

## 寫法的四個原則

需求方逐題看過之後定下來的，寫在 seeder 的類別註解裡：

1. **對象是站台，不是商戶。** 我們的客戶是站台，商戶是站台底下的下游。
   所以 `agent` 稱「代理帳號」而不是「商戶號」；遇到需要設定的事
   （IP 白名單、餘額調整）是**教站台怎麼自己操作**，不是說「我們幫您處理」
2. **一題只講一個錯誤。** 把好幾個錯誤碼塞進一題，客人還是得自己找。
   相似的錯誤（`-4` 與 `10007`、`-2` 與 `-3`）在答案裡說明差在哪，比較另開一題
3. **不要列完整代碼表。** 對站台沒有意義，那在 API 文件裡有。
   他們要的是「遇到這個狀況怎麼解決」
4. **答案裡不要用 Markdown 標記。** 送 Telegram 時用的是 HTML parse_mode，
   `**粗體**` 不會被渲染，客戶會看到字面的星號

### ⚠️ 不能說「我們幫您查」

**客服看不到客人的資料。** 所以答案不能出現
「我們為您查詢系統紀錄」「我們可以查到當初推送的紀錄」這類說法。

統一改成**請商戶提供開單參數 Request**，再加上「我們協助您一起確認」。
需要的是 Request 而不是訂單號 —— 訂單號查不到東西，Request 才看得出問題。

其中 **2 題是反問型**（訂單狀態碼、代收必填欄位）——
代收與代付的定義不同，先問清楚再答，不要把兩種混在一起講。

### 刻意沒做的

`config/errors.php` 還有 `SPIDER_DEPOSIT`（爬蟲寫入）與 `STORE_MEMBER`（商城登入），
那兩組商戶的 API 碰不到，做了只是佔 prompt。

**也不做「一個錯誤碼一題」的完整對照表** —— 那會多出 60 幾題，
而題庫每次呼叫都要整份送進 prompt，額度會被吃光
（見 [auto-reply.md](auto-reply.md) 的風險章節）。

## 第三個來源：商戶串接文件

後來補讀了主系統的 API 文件
`resources/views/skins/architect/docs/content.blade.php`（1,794 行）。

這份是**商戶視角**的，補上了程式碼裡看不出來的東西：

- 加簽：**值為 NULL 的參數不加入組合**、中文要 url encode、
  `api_key` 是接在字串最後而**不參與排序**
- **有線上加簽測試工具** `{api-domain}/api/try-sign`
- `10004` 請求頻率異常的真正定義是「**同一個訂單號**每秒僅一次」
- 回調要回 `OK`、sign 只驗 Parameters 內的參數
- 系統時區 GMT+8、API_KEY 在後台個人資訊頁

### ⚠️ 文件與實作不一致（已用實作為準）

API 文件寫回調的 status 是「00 處理中／01 成功／**02 拒絕**」。

但 `app/Payments/Payment.php` 的 `callbackRecordToAgent()` 是
**直接把 DB 的 status 送出去、沒有轉換**：

```php
'status' => $record->status, // 註解寫 00:處理中, 01:成功, 02:拒絕
```

所以實際值是 DB 的狀態碼：

| 回調 status | 代收實際 | 代付實際 | 文件寫 |
|---|---|---|---|
| `02` | **群組單成功** | 失敗 | 拒絕 |
| `03` | **失敗** | — | **沒列** |

文件的說明**只對代付正確**。客服若照文件回答代收的問題會答錯 ——
題庫已用實作為準。

這件事值得回報給主系統開發修文件。

另外文件也落後於實作：代收 Response 只列到 `-17`（缺 `-18`～`-21`），
代付只列到 `-18`（缺 `-19`）。題庫用的是 `config/errors.php` 的完整版。

### 測試餘額沖正（完整 SOP）

來源是需求方提供的「測試餘額沖正教學」手冊。
商戶測試完要沖正，否則測試單會進入餘額下放、造成對帳金額對不起來。

| 對象 | 狀態 | 處理 |
|------|------|------|
| 代收單 | 待處理 | 狀態設定 → **作廢** |
| 代收單 | 成功 | **退款**，產生 `-1000.000000(refund)` 紀錄 |
| 代付單 | 待處理 | 狀態設定 → **失敗** |
| 代付單 | 成功 | 見下方三步驟 |
| 餘額 | — | 商戶代理總覽 → 設定選擇 → 餘額設定 → 扣除額度 |

⚠️ **成功的代付單預設改不了失敗**，要先到
「系統管理 → 全局預設值設定」開啟「代付沖銷帳務（成功改失敗）功能」，
改完**還要關掉**。這個開關光看程式碼推不出來。

餘額扣除後系統 BOT 會推一則後台操作訊息（操作者／商店號／當前點數／
扣除點數／最後點數／備註），可以用來核對。

### 錯誤碼要「代碼 + 訊息」配對

主系統的錯誤碼分散在兩個檔案：

- `config/errors.php` —— 代碼（`-4`、`10001`）
- `resources/lang/tw/errors.php` —— 對應的中文訊息

API 回給商戶的是 `{"code": -4, "msg": "金額異常"}`，
**只寫訊息不寫代碼的話，客人拿著代碼對不上**。

### 簡體字與錯字已修

主系統的文案混著簡體與錯字，這些會**原文送給客戶**：

- 「订单異常」→「訂單異常」
- 「持有人銀**銀**行名稱必填」→「持有人銀行名稱必填」

## 上線步驟

```bash
php artisan migrate
php artisan db:seed --class=QuickReplyKnowledgeSeeder
```

執行時會做三件事：

1. **新增**還沒建過的題目
2. 列出**後台內容與 seeder 不同**的題目，並詢問要不要覆蓋
   （預設否，直接 Enter 就是保留後台現有內容）
3. 列出**已被拆掉或改寫的舊 key**（`RETIRED_KEYS`），提醒到後台停用

第 3 點 seeder 不會自動刪除 —— 那些題目可能已經被客服改過。

有新增或更新時會自動清掉題庫 prompt 快取（不清的話新題目不會生效）。

跑完建議到「快速回覆題庫」頁把語氣看過一遍 —— 這些答案會原文送給客戶。

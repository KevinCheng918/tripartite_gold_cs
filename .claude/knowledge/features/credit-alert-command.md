# 用 Telegram 指令發餘點告警給客戶

> 需求（2026-10-13）：「我會打，傳餘點告警給某站，要去同步當下點數，然後傳送
> 補點通知給他，這個要有二次確認，補點通知流程可以參考站台列表的補點通知按鈕」
>
> 補充：「如果站台管理的補點通知的按鈕是 disable，就不能繼續動作下去」

```
@機器人 傳餘點告警給 LV_UAT
  ↓ 解析 → 權限 → 找站台 → 檢查缺不缺設定
⚠️ 要發餘點告警給客戶嗎？
   站台：LV_UAT ｜ 發到：某某客戶群        【確認發送】【取消】
  ↓ 按確認（再驗一次權限、再檢查一次設定）
正在同步點數並發送…
  ↓ StationCreditAlertService::sendManual()
✅ 已發送，當下點數：16390.94
```

## ⚠ 這是唯一會發給客戶的查詢類指令

其餘四支（公告預約、查餘點、查虛擬機、預約提醒）都只回在內部群組。
這一支會把兩則訊息**送到客戶的 Telegram 群**，而且**發出去收不回來**。

所以每個環節都往「寧可不發」倒：

| 關卡 | 做法 |
|---|---|
| 權限 | 獨立的 `telegram_chat.credit_alert` |
| 二次確認 | 要，而且確認訊息寫明**發到哪個群組** |
| 按鈕時效 | 30 分鐘，過期作廢（草稿存 Cache） |
| 按鈕的人 | **再驗一次權限**（可能不是下指令的人） |

### ⚠ 權限要檢查在 `pull()` 之前

草稿用 `Cache::get()` 看一眼 → 驗權限 → **確定要發了才 `pull()`**。

顛倒過來（先 pull 再驗）的話，沒權限的 B 按一下就把草稿消耗掉，A 的待確認
跟著失效、得重打一次指令。**B 沒有權限做任何事，更不該有能力把別人的
待確認弄掉。**

被擋時**另發一則**而不是 `editMessage`：編輯的話 B 按一下就把 A 的按鈕蓋掉。
草稿沒被消耗，所以那顆按鈕仍然有效。

`get()` 到 `pull()` 之間還有一小段，所以 pull 回來要再判一次 blank ——
兩個人同時按時，只有先 pull 到的那次會真的發。

本機驗過：用沒綁帳號的 telegram id 按下去，草稿仍在。
| 缺設定 | 給按鈕之前就擋，按下去時再檢查一次 |

## 送出走 `sendManual()`，不重寫

需求方指定「參考站台列表的補點通知按鈕」—— 那顆按鈕走
`StationCreditAlertService::sendManual()`，它已經包含：

1. 檢查有沒有 `telegram_group_id`
2. **先同步點數**（同步不到就不發 —— 不送出過期的數字）
3. 發第一則：餘點告警
4. 發第二則：補點訊息（附繳款圖）
5. 記 `credit_alerted_at`

指令直接呼叫它。**不另外寫一份** —— 兩邊的規則（不管門檻照發、同步失敗不發、
附圖）日後一定會分岔，而分岔的那一邊是在對客戶發訊息。

### 「發出去了，但不完全如預期」要講出來

`sendManual()` 回的旗標要原樣轉達，不講的話按的人會以為客戶收到完整兩則：

| 旗標 | 要講什麼 |
|---|---|
| `below !== true` | 點數其實高於門檻，仍依指示發送 |
| `has_template !== true` | 這個系統沒填補點訊息，**只發了告警那則** |
| `has_rate !== true` | 今日匯率沒決定，**只發了告警那則** |
| `topup_sent !== true` | 告警送出了但補點訊息掛了 —— **客戶只收到一半** |

⚠ 「匯率未定」與「沒填補點訊息」要分開講。混成一句的話，看的人會去查匯率，
但匯率可能好好的（後台那顆按鈕也是這樣分的）。

⚠ 這些都是**布林**，一律 `(bool)` 判斷，不能用 `filled()` ——
`filled(false)` 回的是 true（見 [[2026-10-12-filled-on-boolean]]）。

## 缺設定就不往下走

> 「如果站台管理的補點通知的按鈕是 disable，就不能繼續動作下去」

判斷直接用 **`Station::$topup_notice_blockers`** —— 跟
`resources/views/admin/station/partials/topup-notice-button.blade.php`
**同一個來源**（缺 `api_url` / `api_key` / `telegram_group_id` 任一個就不行）。

⚠ **不自己列一份「要哪些欄位」。** 各寫一份的話，日後多一個必要欄位只會改到
其中一邊 —— 後台按鈕灰了，指令卻還發得出去。

⚠ 回話要把**缺的欄位講出來**（跟後台 tooltip 一樣），欄位名 → 中文走
`station.topup_notice_missing.*` 同一組語系鍵，兩邊講的名字才一樣。

⚠ 檢查**兩次**：給按鈕之前，以及按下去的時候。確認訊息留在群組裡的那 30 分鐘內，
有人可能把 api_key 或群組清掉。

## 確認訊息寫什麼

```
⚠️ 要發餘點告警給客戶嗎？

站台：LV_UAT
發到：某某客戶群

會先同步一次最新點數，然後發兩則給客戶：餘點告警、補點訊息（附繳款圖）。
發出去收不回來。
```

⚠ **「發到哪個群組」是最重要的一行。** 站台名打錯時，看到的人要能從群組名字
認出「這不是我要發的那個」。

⚠ **不顯示目前點數。** 資料庫裡那個值可能是好幾天前的，而實際發出去的是同步後
的新值 —— 先給一個會變的數字只會誤導。

## 權限：`telegram_chat.credit_alert`

介面上：**帳號管理 → 編輯帳號 → 權限設定 → Telegram 客服 → 用指令發餘點告警給客戶**。

⚠ **不跟 `telegram_chat.station_credit`（查餘點）共用**：
看得到點數不等於可以替公司發通知給客戶。這一項跟其他 tg 指令不是同一個層級。

⚠ 管理者（admin）bypass 所有權限檢查（`User::hasPermission()` 第一行）。

## 分派器的順序

```
公告 → 【發餘點告警】→ 查餘點 → 查虛擬機 → 預約提醒
```

⚠ **發告警擺在查餘點之前**：兩者都提到「點數」。萬一兩邊都想認領，先問會發的
那支比較安全 —— 查詢被誤判成發送，至少還有二次確認擋著；反過來則是使用者想發
卻只拿到一個查詢結果，會重打好幾次。

實測兩層都判對（不只靠順序）：

| 說的話 | 告警解析器 | 餘點解析器 |
|---|---|---|
| 傳餘點告警給LV_UAT | `alert` ✓ | `not_credit` ✓ |
| 幫我發補點通知給lv-uat | `alert` ✓ | `not_credit` ✓ |
| 幫我查一下LV_UAT餘點 | `not_alert` ✓ | `credit` ✓ |
| 確認Rich還剩多少點 | `not_alert` ✓ | `credit` ✓ |
| 我lv-uat的點數夠扣這期的虛擬機費用嗎 | `not_alert` ✓ | `not_credit` ✓ |
| 幫我查一下LV_UAT虛擬機 | `not_alert` ✓ | — |

prompt 裡特別寫了「注意『查』跟『發』的差別」—— 認錯的代價不是回錯話，
是客戶收到一則不該收到的告警。

### ⚠ 上線後第一次用就被公告擋住（2026-10-13）

使用者打「@機器人 發送餘點告警給 lv uat」，機器人回的是**公告**的求助文：

> 我看不懂這則公告要什麼時候發、發哪一則、發給誰🙏
> 可以這樣說：・20 分鐘後發送 T01 公告給 LV_UAT …

公告解析器排**第一棒**，它看到「發送…給…」就判成 `unknown`
（＝「是公告，但時間／代號／對象缺了」），於是公告那支認領並回話，
告警那支**根本沒輪到**。

⚠ **我的測試有盲點**：我測了新的告警解析器，也測了它下游的餘點解析器，
**但沒測上游的公告解析器**。加一支指令時，要測的是**整條鏈**，
不只是新的那支跟它旁邊那支。

修法是補公告的 prompt（明列「發餘點告警／補點通知／查餘點／查虛擬機／排提醒
都不是公告」，並說明「不要因為有『發送』『給某某』就當成缺資訊的公告」）。
實測八句：三種告警講法與兩種查詢全部 `not_broadcast`、兩種真公告仍正確解析出
代號與對象、「幫我發個公告」仍是 `unknown`。

### 這個模式已經出現兩次

| 被擋的指令 | 擋住它的 | 原因 |
|---|---|---|
| 試算「夠不夠扣」 | 查餘點 | 過度認領（句子裡有「點數」） |
| 發餘點告警 | 預約公告 | 判成 `unknown`（句子裡有「發送…給…」） |

第二種比第一種麻煩：**`unknown` 等於「我不確定」，但先問到的那一支會
直接把話講掉**，後面的沒機會。目前是靠把每支 prompt 調準來處理，
但這治標。

結構解（尚未做，待需求方決定）：讓 handler 回三態而不是 bool ——
`true`（我處理了）／`false`（不是我的）／`unknown`（像是我的但資訊不足）。
分派器跑完所有指令後，沒人認領才回報第一個 `unknown` 的求助文。
這樣「我不確定」就不會壓過「我確定」。

## 待釐清 / 已知缺口

- **本機沒有已綁定 Telegram 的帳號**，所以「有權限 → 確認 → 真的發出去」
  這條路**沒有端到端測過**。解析與權限邏輯跟線上在跑的公告指令相同。
- **沒有真的發送過**（會送到客戶群，不能拿正式站台試）。`sendManual()` 本身
  是站台列表那顆按鈕一直在用的，沒有改動。
- 確認按鈕 30 分鐘過期；超過會回「請重新下一次指令」。

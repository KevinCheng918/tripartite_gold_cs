# 撤銷請假（v4.10，已實作）

> 需求方 2026-11-24：「現在有人員申請請假了，假別是特休，但是他現在想
> 撤銷請假，我想要做一個功能是撤銷請假，然後也要經過同意，審核撤假
> 也是吃權限，撤假的話要保留請假、撤假紀錄，但是原本的已請假時數部分
> 要扣回，如果有扣掉特休時數、天數的話，要加回，加回部分在審核撤假時的
> modal，做一個勾選框框，預設打勾，打勾代表加回被扣的時數，不打勾就只是
> 單純銷假而已，因為舊資料的關係，之前是沒有扣的，不能因為舊資料，
> 加了時數。」
>
> 追加：「先人為判斷吧，因為目前的只有一筆要手動處理而已，
> 等我正式站手動撤銷完，就可以把這個勾選拿掉了。」

---

## ⚠⚠ 先講一件跟需求描述不一樣的事：**特休額度沒有被「扣」過**

需求的說法是「已請假時數要扣回」「扣掉的特休時數要加回」——
那是**有一本帳、扣款時寫進去**的心智模型。

但這個系統不是那樣做的。`LeaveQuotaService::summaryFor()` 裡，
已用時數是**每次當場算出來的**：

```php
$used = $this->minutesIn($user, $period_start, $period_end, STATUS_APPROVED);
//       ↑ 把「這個特休年度內、type=annual、status=已通過」的假單
//         minutes 全部加總
```

`leave_request` 表裡**沒有任何欄位存「扣了多少」**，
也沒有一張額度帳表。所以：

| 需求的說法 | 這個系統實際上是什麼 |
|---|---|
| 「扣掉特休時數」 | 那張單被**算進**已用的總和裡 |
| 「把時數加回」 | 讓那張單**不再被算進**總和裡 |

⚠ **這不是語意上的吹毛求疵，它決定了怎麼做：**
只要把那張單的狀態改掉（不再是「已通過」），
**額度就自動回來了，不需要任何「加回」的動作**。

而「不加回」反而才是需要特別做的那一件事 ——
得讓一張**已經撤銷的單仍然算進已用時數**。

---

## 所以勾選框真正控制的是什麼

| 勾選 | 畫面上的意思 | 實際行為 |
|---|---|---|
| ☑（預設） | 加回被扣的時數 | 那張單**不再計入**已用特休 ⇒ 額度回來 |
| ☐ | 只是單純銷假 | 那張單**仍然計入**已用特休 ⇒ 額度不動 |

⚠ 文案要照需求方的說法寫（「加回被扣的時數」），
**不要寫成「不再計入已用時數」** —— 後者是實作的語言，
而按那顆按鈕的人想的是前者。

### ⚠⚠ 這顆勾選框是**暫時的**

> 需求方：「先人為判斷吧，因為目前的只有一筆要手動處理而已，
> 等我正式站手動撤銷完，就可以把這個勾選拿掉了。」

所以**不要**去做「自動判斷這筆當初有沒有扣」那套 —— 用不到，
而且判斷依據本來就不可靠。

⚠ **要設計成好拿掉**：勾選框、`restore_quota` 欄位、
以及額度計算裡那個例外分支，三處都要標上同一個記號
（搜尋 `TEMP-CANCEL-KEEP-QUOTA` 就找得齊），
拿掉時才不會漏掉其中一處。

⚠ 拿掉之後，**既有的那幾筆仍然要照舊行為**（＝仍然計入）——
所以欄位本身不要刪，只拿掉「讓人選」的那一步。

## 流程

```
① 同仁對一張「已通過」的假單按「申請撤銷」
      ↓  （留下撤假紀錄：誰申請、什麼時候、為什麼）
② 狀態：撤假待審核
      ↓  有權限的人審（吃 leave_request.review_cancel）
③ 審核 Modal：通過／拒絕　＋　☑ 加回被扣的時數（預設打勾）
      ↓
   通過 → 原假單狀態改成「已撤銷」；勾選決定它還算不算在已用時數裡
   拒絕 → 原假單維持「已通過」，撤假紀錄留著（看得出他申請過又被拒）
```

⚠ **撤假要經過同意**（需求方指定）——
不是按了就撤。這跟請假本身一樣是兩階段。

## 資料怎麼放：**另開一張撤假紀錄表**

> 「撤假的話要保留請假、撤假紀錄」

⚠⚠ **不要只在 `leave_request` 上加幾個欄位然後把狀態改掉。**
那樣「他撤過假」這件事會變成一個狀態值，而
**誰申請撤的、為什麼、誰審的、審核時勾了沒** 全都沒地方放。

```
leave_cancel_request
├─ leave_request_id   哪一張假單
├─ requested_by       誰申請撤的
├─ reason             為什麼要撤
├─ status             0=待審核 1=已通過 2=已拒絕
├─ reviewed_by / reviewed_at / review_note
└─ restore_quota      審核時那個勾選框的結果（⚠ TEMP-CANCEL-KEEP-QUOTA）
```

`leave_request` 只多一個狀態值：

```php
public const STATUS_CANCELLED = 3;   // 已撤銷
```

⚠ **原假單的 `status`／`minutes`／`type` 一個字都不改**（除了狀態）——
那是他當初請了什麼的紀錄，改掉就查不出原貌了。

## 額度計算要怎麼改

現在是：

```php
$used = minutesIn(..., STATUS_APPROVED);
```

要變成「已通過的」＋「撤銷但不加回的」：

```php
// ⚠ TEMP-CANCEL-KEEP-QUOTA：第二段是暫時的，見本檔「這顆勾選框是暫時的」
$used = minutesIn(..., STATUS_APPROVED)
      + minutesOfCancelledKeepingQuota(...);
```

⚠⚠ **這一段動到的是正在運作的額度計算**，而且錯了不會報錯 ——
只會讓某個人的特休多出或少掉幾小時，而他要到請不了假的那天才發現。
所以：

1. 撤假**沒發生過**的人，`used_minutes` 必須**一個數字都不變**
2. 撤銷且**加回**的，`used_minutes` 要少掉那張單的分鐘數
3. 撤銷且**不加回**的，`used_minutes` 要**完全不變**
4. `canAfford()`（申請時的檢查）也走同一套，不能只改摘要那一支

⚠ `pending_minutes` 也要想：撤假待審核期間，那張單還是「已通過」，
所以額度照常被算 —— 這是對的，**撤假還沒通過就不該先把額度還他**。

## 權限

| keyword | 誰用 | 說明 |
|---|---|---|
| `leave_request.cancel` | 申請人 | 對自己已通過的假單申請撤銷 |
| `leave_request.review_cancel` | 審核者 | 審撤假（需求方：「審核撤假也是吃權限」） |

⚠ **`review_cancel` 要獨立，不要併進既有的 `leave_request.review`** ——
審請假與審撤假是兩種決定（後者會動到額度），
併在一起就沒辦法只給其中一種。

## 已定案（需求方 2026-11-24 拍板）

| # | 問題 | 決定 |
|---|---|---|
| 1 | 誰可以申請撤假 | **只有本人** |
| 2 | 待審核的假單 | **不走撤假流程**，直接取消就好（還沒生效，撤掉不影響任何人） |
| 3 | 已開始／已過去的假 | **不能撤**，只能撤還沒開始的 |
| 4 | 撤假審核完的通知 | **要，而且單獨發一則**給申請人 |
| 5 | 勾選框 | **照做**（見下面那一節的更正） |

### ⚠⚠ 第 3 點與勾選框的關係（我一度判斷錯，更正在此）

我先前說「只能撤未開始的假 ⇒ 那顆勾選框按了也不會有差別」——
**那句話說過頭了。**

正確的是：勾選框**仍然有明確的效果**。未開始的特休假一定被算進已用，
所以撤銷時：

- ☑ → 不再計入 ⇒ 額度**回來**
- ☐ → 仍然計入 ⇒ 撤了假，但這段特休**仍算他用掉了**

兩者結果不同。失效的只是它**原本的理由**（「舊資料當初沒扣」——
舊資料是過去的假單，在第 3 點之下進不了這個流程），不是它的作用。

⚠ 所以它不是一顆沒作用的按鈕，而是一顆**原始動機已經不適用、
但語意仍然成立**的按鈕。拿掉它的時機由需求方決定，不是因為它壞了。

### 第 2 點的做法：取消 vs 撤銷是兩個東西

| | 待審核的單 | 已通過的單 |
|---|---|---|
| 動作叫什麼 | **取消申請** | **申請撤銷** |
| 要不要審核 | **不用**，按了就掉 | **要**（需求方指定） |
| 額度 | 本來就只算在 `pending_minutes`，取消後自然消失 | 看勾選框 |
| 留不留紀錄 | 原單狀態改成已取消（留著） | 原單 ＋ 撤假紀錄都留 |

⚠ **兩件事不要共用同一個按鈕與同一條流程** ——
混在一起會讓「我剛剛按錯了」也要等人審才撤得掉。

### 第 3 點的判斷基準：`start_date > 今天`

⚠ **用「開始日還沒到」而不是「結束日還沒到」**：
一張 11/20–11/25 的假，到了 11/22 已經請掉三天了 ——
那不是「還沒開始」，不該讓人撤。

## 實作完成（v4.10，2026-11-24）

### 驗證到哪（全程交易內 rollback）

**額度**（最危險的一段 —— 算錯不會報錯，只會讓某個人的特休多出或少掉）

| 情境 | 期待 | 結果 |
|---|---|---|
| 開一張未來的特休（720 分） | 已用 +720 | ✓ |
| 申請撤銷、**還在等審** | 已用**不變**（還沒通過不該先還他） | ✓ |
| 審核通過 ＋ **打勾** | 已用 −720，原單狀態 3 | ✓ |
| 審核通過 ＋ **不打勾** | 已用**完全不變**，原單狀態 3 | ✓ |
| 審核**拒絕** | 已用不變，原單狀態**仍是 1** | ✓ |

**擋人的條件**

| 情境 | 結果 |
|---|---|
| 別人來撤 | 擋下：只能撤銷自己的請假 |
| 同一張單重複申請 | 擋下：已經有一筆在等候審核 |
| 今天開始的假 | 擋下 |
| 已經過去的假 | 擋下 |
| **請到一半的假**（起 −2 迄 +2） | **擋下** ⚠ 這是最容易漏的邊界 |
| 對待審核的單「申請撤銷」 | 擋下：只有已通過的才需要 |
| 對待審核的單「取消」 | ✓ 成功，狀態變 3 |
| 對已通過的單「取消」 | 擋下：請改用「申請撤銷」 |
| 同一筆撤假審兩次 | 第二次擋下 |
| 被拒絕後再申請 | ✓ 成功，**兩筆紀錄都留著** |

**前端**：兩個 Modal 都在、勾選框**預設打勾**、五個分頁無 JS 錯誤；
三條路由都走得到 model binding（權限沒擋）。

### ⚠ 實作時踩到的

`ApprovalNoticeService` 漏了 `use App\Models\LeaveCancelRequest;` ——
型別提示解析成**同命名空間**的 `App\Services\LeaveCancelRequest`，
丟 `TypeError`。⚠ 這個錯**只有在真的呼叫到那一支時才會出現**，
`php -l` 看不出來。

### ⚠ 既有 Modal 被借來當二次確認

這個專案沒有通用的 confirm（而且需求方明訂不准用 `alert`），
所以「取消待審核申請」借用了既有的 `modal-leave-confirm`。

⚠ 那個 Modal 現在有**兩種用途**，靠 `leave-confirm-status` 的值分辨：
`1`／`2` 是請假審核，`cancel-pending` 是取消申請。
少了這一層，`parseInt('cancel-pending')` 會變成 `NaN` 然後送出一個
status 不合法的審核請求。

### ⚠ 管理者看不到「我的請假」

`renderLeave()` 是 `if (!isAdmin && hasPerm('leave_request.apply'))` ——
**管理者那一側不顯示自己的請假清單**（既有行為，不是這次改的）。
所以「申請撤銷」那顆按鈕用 admin 帳號**測不到**，要用一般帳號。

### ⚠ 上線要記得

1. `php artisan migrate`（`leave_cancel_request`）
2. `php artisan optimize`（`permissionMap` 加了兩個 keyword）
3. **到權限設定頁指派** `leave_request.cancel` 與
   `leave_request.review_cancel` —— 不指派的話那兩顆按鈕沒有人看得到

### 稽核修掉的（v4.11，按 PROMPTS.md 逐項對照）

**兩支死碼**：`LeaveCancelRequestRepository` 的 `find()` 與 `getPending()`
寫了但沒有任何人呼叫 ——

- 審核走的是**路由模型綁定**（`{leaveCancelRequest}`），不需要 `find()`
- 撤假的入口掛在**請假清單那一列**上（`latestByLeaveIds()`），
  沒有獨立的待審清單

⚠ **repository 的方法不同於 model 的關聯**：前者暗示「系統裡有人這樣查」，
後者只是在描述資料長什麼樣。所以兩支方法砍掉，
而 `leaveRequest`／`requester`／`reviewer` 三個關聯留著。

⚠ 已在原處留下註解說明為什麼「刻意沒有」這兩支 ——
不然下一個人會以為是漏寫的。

其餘逐條都過：PHPDoc 齊、Controller 沒有商業邏輯、沒有未使用的 import、
無 `SELECT *`／N+1／`isset`／`??`／`empty`／`!filled`／`fn`、
多表寫入在 `DB::transaction` 內、三語系同步、前端讀得到所有新文案。

⚠ **已知的小瑕疵（沒有改）**：撤假的 UI 標籤（`cancel_action`、
`cancel_title` 等）放在語系檔的 `msg` 陣列底下，而那一區原本是放
「訊息」的。blade 與 JS 兩邊都一致地用 `leave.msg.*`，所以功能正常 ——
但位置語意上不精確。要搬的話兩邊都得改，這次沒動。

## 補修（v4.18，2026-11-25）：狀態欄印成「-」

> 需求方：「撤銷的請假，狀態這邊要是已撤銷」

`STATUS_CANCELLED = 3` 在 v4.10 就加好了、後端也確實寫進去，
但**前端那張對照表只做到 2**：

```js
leaveStatusMap[0] = 待審核;  leaveStatusMap[1] = 已通過;  leaveStatusMap[2] = 已拒絕;
// 3 沒有 → 第 2301 行的 fallback 印出 '-'
var st = leaveStatusMap[item.status] || { text: '-', css: '' };
```

⚠⚠ **一般化：新增狀態常數時，「寫得進去」與「顯示得出來」是兩件事。**
後端的 enum／常數加了、服務也寫對了，但前端的對照表、語系檔若沒跟上，
使用者看到的是 `-`（像資料壞掉），而不是新狀態。
這個專案的狀態對照表有三張，都在 `public/js/shifts.js`：
`swapStatusMap`（換班）／`coverStatusMap`（代班）／`leaveStatusMap`（請假）。

⚠ 用**灰色**（`bg-secondary`）不用紅色 —— 撤銷是申請人自己收回，
跟「被主管拒絕」是兩回事，同樣染紅會讓人以為他被打回票。
（這套後台的 badge 是自訂的淡色底，`bg-secondary` 淺／深兩套都有，已量過。）

語系三邊都補了 `status_cancelled`。

## ✅ 已回答：撤銷之後那天還能不能排班／打卡

> 需求方 2026-11-25：「確認一下排班，如果是有請假成功，又撤銷的話，
> 當天可不可以排班，然後打卡也要確認，被撤銷那天能不能打卡上班」

**兩個都可以。** 不是用讀的推論，是真的跑過 `ShiftService::assign()`
與打卡那一關（交易內 rollback）：

| 階段 | 排班 | 打卡 |
|---|---|---|
| 還沒請假 | 可以 | 可以 |
| 請整天假・已通過 | **擋下**「該日有已通過的請假，無法排班」 | **擋下**「當天請假中」 |
| 撤假通過（status=3） | **可以** | **可以** |

### 為什麼不用額外改任何東西

⚠ **所有「這天有沒有請假」的查詢都只認 `STATUS_APPROVED`。**
`LeaveRequestRepository` 七處狀態條件裡，六處是 `where('status', APPROVED)`，
剩下一處是 `hasOverlapping()` 的 `whereIn([PENDING, APPROVED])`。
狀態一旦變成 3 就自動從每一處掉出來 —— 排班、打卡、曠工標記、
打卡提醒、月報表全都共用這幾支。

附帶驗過的：撤銷後 `getApprovedOnDate` 0 筆、
`fullDayLeaveMapByDateRange` 0 天、`hasOverlapping` 不擋
（同一天可以重新請一次假）。

⚠ **但要知道的副作用**：撤的如果是**已經過去**的假，那天在出勤時間軸上
就不再是「請假」了。該上班卻沒打卡又沒有曠工紀錄的話，會顯示成
「無打卡紀錄」（見 [[attendance]] 的四種情況）—— 這是撤銷過去的假
本來就會有的結果，不是 bug，但撤之前要意識到。

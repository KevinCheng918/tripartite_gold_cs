# 交接漏項盤點：AI 比對交接內容，沒寫到的**一題一題**問要不要補（v4.00）

> 需求方 2026-11-19：「各班交接，我要多一個功能，整理上一個班有的問題，
> 然後 AI 比對有沒有交接到，詢問沒有寫到的要不要補上。」
>
> ⚠⚠ **2026-11-23 改掉了原本的整批選單**，改成一問一答。
> 見下面〈一問一答長什麼樣〉—— 整批選單那個形狀不要再回去。
>
> 追加：「最後一項是提醒交接的人，主管、老闆有沒有交代什麼事項是要注意的、
> 要待辦的，是不是也要列上去。」
>
> 當天確認的兩件事：
> - 來源 = **求助單 ＋ 待追蹤事項 ＋ 預約提醒**（任務卡這一版不收）
> - 按「補上」＝ **系統貼客觀事實 ＋ tag 他補一句現況**（不代替他做判斷）

## 這個功能在補什麼洞

現在的交接（v3.81）只確認「**有沒有打**」——
`ShiftHandoverService::detect()` 看到那一班的人在交接話題發言就算完成，
**內容一個字都沒看**。所以「沒有」兩個字就能結案，而那一班其實留著
三張沒人回的求助單。

這一版補的是「**打的內容夠不夠**」：系統手上本來就有那一班發生過什麼，
拿去跟他打的內容比對，漏掉的當場問他要不要補。

⚠ **不是在考核交接寫得好不好。** 只比對「這件事有沒有被提到」，
不評價寫得清不清楚 —— 後者沒有客觀標準，而且會讓這則通知變成找碴。

## 觸發時機：他打完交接的當下

掛在 `markHanded()` 之後，派 `HandoverReviewJob` 背景跑
（AI 要幾秒，webhook 不能等 —— 同 `ReplyTicketJob` 的理由）。

⚠ **不是等窗口結束才總結**：那時人已經下班了，補不動。
打完當下他還在現場，而且腦袋裡還有那一班的事。

⚠ **一個窗口只盤一次。** `markHanded()` 只在第一次發言時觸發
（之後 `status` 已是 `HANDED`，`findPendingForShifts()` 撈不到）——
他補充的第二句不會再觸發一輪新的比對，否則話題會被洗版。

## 要盤哪些事（需求方選定）

全部都限定在**上一班的回訊時段**內：`[date + 上一班回訊開始, window_end]`
（`window_end` 就是上一班回訊結束，表上已經有）。

| 來源 | 條件 | 為什麼是它 |
|---|---|---|
| 求助單 `auto_reply_ticket` | 那段時間開的，**到現在還沒結案**（`close_action` 是 null） | 「客人還在等」最直接的訊號 |
| 待追蹤事項 `conversation_followup` | 那段時間開的，現在還掛著 | 我方或客人說了「稍等」還沒給結果 —— 那本來就是承諾 |
| 預約提醒 `scheduled_reminder` | 那段時間排的、**還沒發出去**的 | 下一班要知道等一下會有東西跳出來，而那是上一班排的 |
| **主管／老闆交代的事** | — | **推導不出來**，見下節 |

⚠ **已經結案的不盤。** 那一班自己處理掉的事不需要交接 ——
列出來只會讓清單變長，而長清單沒有人看。

⚠ **每一種都設筆數上限**（`MAX_PER_SOURCE`，預設 5）。
一班開了 30 張單的那天，列 30 項等於沒列 —— 超過就在最後補一句
「另外還有 N 件，請自己到後台看」。

### ⚠ 最後一項是「問句」，不是資料

> 需求方：「最後一項是提醒交接的人，主管、老闆有沒有交代什麼事項是要注意的、
> 要待辦的，是不是也要列上去。」

**口頭交代、私訊交代，系統一個字都看不到。** 所以這一項不是從哪張表撈出來的，
是**固定掛在清單最後的一句提醒**：

```
4. 主管／老闆這一班有交代什麼要注意或待辦的嗎？
```

⚠ **它的「補上」行為跟前三項不一樣**：系統貼不出事實（根本不知道），
所以按下去是 tag 他請他自己打，而不是系統代貼。沒有的話回一句「沒有」。

⚠ **每一次都要出現，不管前三項有沒有漏。** 這一項的價值正是在
「系統完全不知道」的那一塊，用「這次沒別的漏項就不問」來省行數，
剛好省掉最該問的那一句。

## AI 比對

走既有的 `ClaudeCodeMatcher::generateStructured()`（Claude Code CLI，
訂閱制），輸入是他打的交接原文 ＋ 候選清單，輸出每一項
`covered` 與一句理由。

⚠ **只讓模型做「這件事有沒有被提到」這一件事。** 判斷標準寫在 system prompt：
講到同一個客人群組＋同一件事就算提到，用字不必一樣（「超商那個」
算提到「上游 API 新增超商」）。不要讓它判斷寫得夠不夠詳細。

⚠ **模型掛掉／沒設憑證時不要整個不發**（同其他幾支的原則）：
退成「沒有比對，這是這一班的全部清單」，選單照出。
少了過濾會多問幾項，但漏掉才是真的出事。

⚠ **候選一項都沒有時整個不發。** 那一班真的沒事 —— 發一則
「沒有漏掉的」只是噪音。但最後那一項（主管交代）**仍然要問**，
所以那時發的是只有一項的選單。

## ⚠⚠ 一問一答長什麼樣（v4.00 改掉了原本的整批選單）

> 需求方 2026-11-23：「我不要用選項，我要用**一個問題一個問題問**，
> 然後不要單一去變，我要**留下紀錄**：一個問題，問出來，由交接班的人去選擇，
> 選完之後就補充到對話，繼續問下一題，這樣無論是下一班的人或是主管、老闆
> **回過頭來看才知道斷在哪裡**。」

### 流程

```
開場（一則，不帶按鈕）
📋 這一班有 2 件事看起來沒寫進交接（早班）
　@mary 我一題一題問，您答完一題我就接著問下一題。
ℹ️ 另外還有 7 件沒列出來，請到後台看
      ↓
❓ 第 1 題（共 3 題）
• LV 群：上游 API 能不能自己新增超商
　求助單 #123，已等 3 小時，還沒人回
@mary 這件要補進交接嗎？
[要補上] [不用補]
      ↓ 他按了「要補上」
❓ 第 1 題（共 3 題）          ← 題目**留著**
• LV 群：上游 API 能不能自己新增超商
　求助單 #123，已等 3 小時，還沒人回
@mary 這件要補進交接嗎？
———
✅ 要補上 —— @mary 麻煩在這個話題補一句現在到哪了   ← 答案接在後面、按鈕撤掉
      ↓ 接著才問
❓ 第 2 題（共 3 題）…
      ↓ 全部答完
🧾 交接盤點答完了（早班）　共 3 題
✅ 要補上 1 件
　• LV 群：上游 API 能不能自己新增超商
⏭ 不用補 2 件
　• TR 群：客人在等對帳單
　• 主管／老闆交代事項
@mary 上面要補的，麻煩在這個話題補完
```

### 為什麼是這個形狀

| 決定 | 理由 |
|---|---|
| **一題一則訊息** | 話題本身就是那份紀錄：捲一遍就知道問了什麼、他怎麼答 |
| **答完不換掉題目**，答案接在同一則後面 | 只留答案的話，下一班看到一串「✅ 要補上」「⏭ 不用補」，根本不知道在答什麼 |
| **最後一則還掛著按鈕的就是斷點** | 需求方要的「知道斷在哪裡」＝不必查後台也看得出他答到第幾題 |
| **開場另發一則、不併進第 1 題** | 第 1 題答完要重組它自己的文字（見下），而「有沒有比對成」「另外還有 N 件」只有發問那一趟知道 —— 併進去一答完就被重組掉 |
| 主管交代那一題按鈕換成 `[有，我補上] [沒有]` | 那題問的是「有沒有」，放「不用補」會變成他在推掉主管交代的事 |

### ⚠⚠ 不要改回整批選單

舊版是一則清單 ＋ `[1 補上] [2 補上] [全部補上] [都不用]`，按完整組換成
「✅ 已補上 3 項」。那個形狀**把整件事壓成一則結果** ——
哪一題怎麼決定的、答到第幾題就沒下文了，全都看不出來。
`constants.HANDOVER_REVIEW.ACTION` 現在只有 `FILL` / `SKIP` 兩個，
沒有 `FILL_ALL`，這是刻意的。

### ⚠ `buildQuestionText()` 必須是「同一列資料 → 同一段文字」

Telegram 的 `editMessageText` 要**整則重送**，沒有「接一段上去」的 API ——
所以答完之後那一則是「重新組一次題目文字 ＋ 答案」。
題目文字裡摻進任何「只有發問那一刻才知道」的東西，一答完就會被重組掉。

### ⚠ 沒有「催到補完」這回事

交接本身是催到完成的（v3.81，因為「他沒有就會打沒有了」），
但**漏項是判斷題** —— 他可能真的覺得那件事不必交接。問一次就好，怎麼答由他。
答完總結就結束，不會再追沒補的那幾件。

## 為什麼需要一張新表

`callback_data` 只有 64 bytes，塞不下「哪一項、內容是什麼」。
所以比對結果要落地：`shift_handover_gap`

| 欄位 | 說明 |
|---|---|
| `shift_handover_id` | 哪一次交接 |
| `source_type` | 1=求助單 2=待追蹤 3=預約提醒 **4=主管交代（固定項）** |
| `source_id` | 來源主鍵（固定項為 null） |
| `title` / `detail` | 當下組好的摘要（**快照**，來源之後變了也不影響已發出的題目） |
| `covered` | AI 判定有沒有被交接到 |
| `status` | 0=還沒答 1=要補上 2=不用補 |
| `seq` | **題號**（`callback_data` 只帶 handover_id ＋ seq） |

⚠ `title`／`detail` 存快照的理由同 `auto_reply_ticket.question`：
按鈕可能半小時後才被按，那時單子早就被處理掉了，重查會查出不一樣的話。
v4.00 之後更重要：答完要**重組一次題目文字**，快照不固定的話
那一則的題目會跟當初問的不一樣。

⚠ `status` 同時是「進度」：`seq` 最小的 PENDING 就是「下一題」，
全部不是 PENDING 就是「答完了」—— 不需要另外一個 `current_seq` 欄位。

## 實作時修掉的三件事（排版實測抓到的）

1. ⚠ **「另外還有 N 件」不能佔題號。** 第一版讓它跟其他項目一起進
   `shift_handover_gap`，結果編號變成 1、2、3、**5** —— 跳號看起來像系統壞掉。
   改成在 `splitNotes()` 就抽出來，不進表、不送比對，接在開場最後。
   （v4.00 之後更嚴重：它會變成一題**問不出答案的題目**，他只能卡在那裡。）
2. ⚠ **總結裡不能直接印主管那一題的 `title`。** 那一題不是從任何一張表撈出來的，
   `title` 是空的 —— 直接印會變成一行空白的「•」。
   所以總結用固定的 `SUMMARY_MANAGER_LINE`。
3. ⚠ **`mentionOf()` 不能回空字串。** 交接人查不到時那句會變成
   「　麻煩補一句現在到哪了」—— 開頭空一格，而且沒有人知道是在對誰說。
   退路三層：`@username` → 暱稱 → `handed_by_name` → 「交接的同仁」。

另外 `isOwner()` 與 `mentionOf()` 問的是同一個帳號（按一次按鈕會查兩次），
所以 `ownerOf()` 做了一個 per-request memo，比照
`UserRepository::$assignableForOwner`。**用 `array_key_exists` 而不是
`filled()`** 判斷查過沒 —— 查不到（null）也要記住，否則每次都會再確認一次
「還是查不到」。

## 稽核時再修掉的五件事（按 PROMPTS.md 逐項對照）

1. ⚠⚠ **「沒東西要比」被當成「比不出來」。** 那一班真的什麼事都沒發生時，
   候選只剩最後那句固定問話 ⇒ `$covered` 也是空的 ⇒ 第一版照 `blank($covered)`
   判斷，選單會印「這次沒辦法自動比對交接內容」——
   **那是在對一個好好交接完的人說謊**。改成 `filled($askable) && blank($covered)`。
2. ⚠⚠ **全都交接到時，標題說他漏了一件。** 那時清單只剩那句問話，
   而 `HEADER` 寫的是「有 1 件事看起來沒寫進交接」——
   指著一個**問句**說他漏了。加 `ALL_COVERED_HEADER`
   （「這一班的事都交接到了 👍　最後確認一件事：」），算數量時扣掉固定問話。
3. ⚠ **模型回的編號沒驗就用。** 它可能回清單外的編號（自己重編過的），
   那個 key 會對到另一個候選，把「其實沒交接到」的事標成已交接而
   **整項從選單上消失**。現在不在 `askable` 裡的一律丟掉並記 warning。
4. ⚠ **沒撈滿上限也去查總數**（第 2 節效能）：撈到的就是全部，那次 COUNT
   是白打的，三個來源各一次。`withMore()` 改吃 closure，只在撈滿時才問 DB。
5. 第 3 節字串插值：`buildKeyboard()` 的 `callback_data` 原本是
   `"{$prefix}:" . Arr::get(...) . ":{$id}"` 這種混合串接，改成先取值再整串插值。

另外補了兩處 log（第 5 節）：交接紀錄查不到、模型回了清單外的編號 ——
兩者都會讓選單默默少東西，沒有 log 就查不出為什麼。

## ⚠⚠ 上線驗證抓到的：送不出去卻留著紀錄 ＝ 永遠問不到的孤兒

`shift_handover_gap` 有沒有紀錄，就是「這次交接問過了沒」的唯一依據
（`existsForHandover()` 靠它擋 Job 重送）。第一版是**先落地再送訊息**，
而送訊息會失敗（沒設支援群組、Telegram 掛掉、話題被刪）——

失敗的那一刻，狀態就壞了：**選單不存在所以沒有人按得到，而下一次重跑
又會被擋下。** 那張交接變成永遠問不到、也永遠不會再問。

修法：`sendMenu()` 回 false 就把剛寫入的整批 `deleteByHandover()` 收回，
並記一行 warning。這樣狀態才一致：**有紀錄 ⇔ 選單真的在話題裡**。

（本機沒有設定內部支援群組，所以這條路是第一次端到端跑就踩到的。）

## 驗證到哪

- DI 解析、選單／按鈕／補充交接三種排版、`splitNotes()` 的分流、
  大夜班跨日的區間起點（`date` 是 11/18、窗口在 11/19，起點要是
  **11/18 23:00**）都在本機用記憶體物件驗過
- **三種開頭各驗一次**（有漏的／全都交接到了／模型掛掉），
  以及 `withMore()` 的短路（撈 3 筆上限 5 ⇒ 0 次 COUNT；撈滿 5 筆 ⇒ 1 次）
  與 `askableIndexes()` 會跳過固定問話
- **`callback_data` 全部在 64 bytes 內**（`hr:f:7:1` 這種長度）

### ⚠ 本機驗不到的兩件事

1. **模型比對**：laradock 容器裡**沒有裝 `claude` CLI**（`which claude` 找不到），
   所以 `generateStructured()` 一定失敗 —— 本機永遠走「沒有比對，全部列出」那條。
   **這剛好驗到退路是對的**（記了 warning、沒有整個不發），但判斷準不準要上線才知道。
2. **Telegram 實際送出**：本機沒有設定內部支援群組。

### ⚠ 佇列：本機 `sync`、線上 `database`

本機 `.env` 是 `QUEUE_CONNECTION=sync`（那樣 Job 會在 webhook 裡同步跑，
等模型十幾秒 ⇒ Telegram 逾時重送），線上是 `database`（需求方 2026-11-20 確認），
所以線上沒有這個問題。

### ⚠⚠ Job 的 `timeout` 必須小於 `retry_after`

`config('queue.connections.database.retry_after')` 是 **90 秒**。
佇列在那之後會認定 Job 卡住而**重新派發一份** —— 同一次交接兩份同時跑，
兩份都叫模型，然後其中一份的 `insertMany()` 撞上
`(handover_id, seq)` 的 unique 而丟例外。
`existsForHandover()` 擋得住「跑完之後的重送」，**擋不住這種併發**。

所以 `HandoverReviewJob::$timeout` 從 180 改成 **80**。
裡面最慢的是模型，而 CLI 自己有 60 秒逾時（`config('auto_reply.timeout')`）。

> ⚠ **既有的兩支 Job 也踩在這條線上**：`AutoReplyJob` 與 `FollowupDetectJob`
> 的 `timeout` 都是 **120 > 90**。它們平常跑不到 90 秒所以沒出事，
> 但模型一慢就會被重派 —— 而 `AutoReplyJob` **會發訊息給客戶**，
> 重派等於客人收到兩份答案。
> 這不是這個功能引入的，修法見文末。

## 待釐清

1. **「都不用」要不要記理由？** 目前只記狀態。之後若想看「哪些項目常常被
   認為不必交接」才需要，這一版不做。
2. **要不要讓下一班的人也能按？** 目前只有打交接的本人按得動
   （按鈕會驗 `from.id` 對不對得上 `handed_by_user_id`）——
   下一班按「補上」會變成他在替上一班承諾。

## ⚠⚠ 待決定（不是這個功能的 bug，但同一條線上）

`retry_after`（90）比 `AutoReplyJob`／`FollowupDetectJob` 的 `timeout`（120）
還短。只要模型慢到 90 秒，佇列就會重派一份 ——

- `AutoReplyJob` **會發訊息給客戶** ⇒ 客人收到兩份答案
- `FollowupDetectJob` 會開待追蹤事項 ⇒ 同一句話開兩筆

兩支都是 `tries = 1`，但 `tries` 擋的是「失敗後重試」，擋不住
「佇列以為你卡住而再派一份」。

一行修法（**沒有改任何 Job 的行為**，只是讓佇列更有耐心）：

```php
// config/queue.php
'retry_after' => 300,   // 要大於所有 Job 裡最長的 timeout
```

⚠ 改完要 `php artisan optimize` **並重啟 queue worker**
（worker 會把設定讀在記憶體裡，不重啟的話還是用舊值）。

⚠ 代價：真的卡死的 Job 要等 5 分鐘才會被放棄。本專案所有 Job 都是
`tries = 1`，所以那只是「晚一點被記成失敗」，不會多跑一次。

### ⚠⚠ 實測抓到的 bug：`markStatus($ids, PENDING)` 退不回去

答完一題之後，下一題（或總結）送不出去時要把狀態退回「還沒答」，
他再按一次就是重試。第一版直接用 `markStatus($ids, PENDING)` ——

```php
// ShiftHandoverGapRepository::markStatus()
->whereIn('id', $ids)
->where('status', config('constants.HANDOVER_REVIEW.STATUS.PENDING'))  // ← 樂觀鎖
->update(['status' => $status]);
```

那個 `where` 是給「PENDING → 其他」用的樂觀鎖，條件剛好把
**FILLED／SKIPPED → PENDING** 這個方向整個過濾掉：更新 0 筆、**不報錯**。

實測結果是 `seq3=2`（該退回 0），再按一次會得到「這一題已經答過了」，
而下一題永遠不會出現 —— **整輪盤點永久停在那一題，沒有人救得了**。

修法：另開一支 `revertToPending()`，條件改成 `status <> PENDING`。
兩支方法的註解都寫明了不可互相代替。

### ⚠⚠ 在這之前整條線是斷的

```
系統：「@他 麻煩把交代的內容補一句在這個話題」
他：  「4.若水跟DM:APK目前使用狀態是否有問題」

```

`shift_handover_gap` 只記了「他**說**要補」，**沒記他補了什麼，
也不知道他到底補了沒**。所以：

- 他補完之後話題一片安靜 —— 看起來像壞掉（需求方就是這樣回報的）
- ⚠⚠ **答了「有，我補上」卻忘記補，沒有任何人會發現** ——

那時我回答「那個話題裡機器人是刻意不回話的」—— 講得不完整。
`AutoReplySupportService::handleSupportMessage()` 的 `isTicketTopic()`
是 2026-11-11 為了擋「交接訊息的 message_id 撞到舊求助單」加的，
但**那個洞靠話題判斷本身就堵住了**；現在的結果是
「因為它不是求助單，所以什麼都不做」，而交接話題有自己該做的事。

### 怎麼認出「這句話是在補哪一題」

需求方選的是「**引用盤點訊息才算**」：

| 他引用的 | 對應到 |
|---|---|
| 某一題 | 那一題（`shift_handover_gap.ask_message_id`） |
| 開場／總結 | 這一輪**第一個「說要補但還沒補」**的題目 |
| 其他（交接事項本身、同仁討論） | **不處理**，照常往下走 |

⚠ **不限定引用的話**，話題裡的交接事項、下一班的交接、同仁之間的討論
全都會被誤記成某一題的補充。

⚠ **需要 migration**：v4.00 把開場／題目／總結送出去之後，
回傳的 `message_id` 直接丟掉了 —— 沒存就反查不回來。

```
shift_handover_gap  + ask_message_id（索引）/ filled_note / filled_at
                    + remind_count / last_reminded_at
shift_handover      + review_opening_message_id（索引）
                    + review_summary_message_id（索引）
```

⚠⚠ **`status` 與「補了沒」是兩件事，不要互相取代。**
`status = FILLED` 只代表他**按了**「要補上」；`filled_at` 才是他**真的補了**。
混在一起的話「答應了卻忘記補」就永遠問不出來。
（`ShiftHandoverGap::needsFill()` 問的正是兩者的差集。）

### 催到補完為止（需求方選的）

⚠⚠ **這跟「漏項只問一次」不衝突** —— 兩者問的是不同的事：

| | 催不催 | 為什麼 |
|---|---|---|
| 要不要補（`[要補上]`／`[不用補]`） | **只問一次** | 判斷題，他可能真的覺得不必交接 |
| 說了要補卻沒補 | **催到補完** | 他已經答應了，這是未完成的事 |

- 間隔 `HANDOVER_REVIEW.REMIND_INTERVAL`（30 分鐘，填 0 不催）
- 第 `ESCALATE_AT`（3）次起連主管一起 tag，沿用交接本身那套名單
- 催的那一則**引用那一題**，所以看得出在催什麼
- ⚠ 文案要寫「第 N 次提醒」：第 3 次被 tag 進來的主管才分得出
  這是剛發生的，還是已經催很久了
- ⚠ **不論 tag 不 tag 得到人，`remind_count` 都要推進** ——
  不推的話這一筆每分鐘都會被重試（求助單、待追蹤、交接本身都踩過）

⚠ **沒有停點**（需求方選的）。要留意的是：離職或長期忘記的人，
那一筆會一直催下去。第 3 次就會連主管一起 tag，所以會很快浮上檯面，
但**這仍然是這次改動要觀察的地方**。

### ⚠ 還沒作答的題目不收

他引用了一題、但那一題還沒按按鈕時，回一句請他先按，**不收內容**。

收下去會變成「資料上補好了、畫面上還掛著按鈕在問」——
兩邊對不起來，下一班看了只會更亂。

### ⚠ 實測抓到：交接人自己就是主管時，第 3 次會 tag 他兩次

```
第 3 次 → @owner_tg @owner_tg @boss1 @boss2 麻煩引用這一則把內容補上來
```

`getManagersForMention()` 撈的是 `level <= LEADER` 的人，而**交接的人
自己就是主管的情況很常見**（小團隊、組長輪班）。修法是
`withoutOwner()` 先把他剔掉。

⚠ **比 `id` 不比 Telegram 帳號**：帳號可能沒填（那時 `mentionOf()`
會退成暱稱），比字串會漏掉。

### v4.05 驗證到哪（2026-11-24，migration 跑完後，全程交易內 rollback）

**收補充**

| 情境 | 結果 |
|---|---|
| 引用**第 1 題**補內容 | 記到第 1 題、回「收到，已經記到第 1 題底下」、**引用他那一則** |
| 同一題**再補一次** | **接在後面**（兩句都在），不是蓋掉 |
| 引用**總結** | 記到第一個還欠著的題目（主管交代那一題），稱呼用固定的「主管／老闆交代事項」而不是空的 `title` |
| 引用**還沒按按鈕**的題目 | 回「請先按按鈕」，**內容沒有被收走** |
| 引用**無關的訊息**（別人的交接事項） | 回 `false`、**不回話**（不會吃掉求助單的作答） |
| 沒有引用／有引用但沒文字 | 回 `false` |

⓪ 先確認 `COLUMNS` 讀得回新欄位 —— 這個專案踩過四次的坑。

**催補**（5 筆，間隔 30 分、第 3 次帶主管）

| 筆 | 狀態 | 該催嗎 | 結果 |
|---|---|---|---|
| A | 要補、沒補、沒催過 | ✅ | 催了，第 1 次 |
| B | 要補、**已經補了** | ❌ | 沒催，`remind_count` 沒動 |
| C | **不用補** | ❌ | 沒催 |
| D | 要補、**25 分鐘前剛催過** | ❌ | 沒催 |
| E | 要補、催過 2 次且已到期 | ✅ | 催了，**第 3 次**、帶主管 |

- 催的那一則**引用那一題**（`ask_message_id`）
- 馬上再跑一次 → **0 筆**（間隔擋住了）
- 第 2 次**不帶**主管、第 3 次帶，且交接人自己不重複

**端到端**：`review()` 存下開場與題目的 message_id → 答「有，我補上」
存下總結的 message_id → 引用總結補內容 → `needsFill()` 從 yes 變 no
→ 不再被催。

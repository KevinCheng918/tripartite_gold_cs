# 交接漏項盤點：AI 比對交接內容，沒寫到的用選單問要不要補（v3.92 已實作，migration 待跑）

> 需求方 2026-11-19：「各班交接，我要多一個功能，整理上一個班有的問題，
> 然後 AI 比對有沒有交接到，詢問沒有寫到的要不要補上，用選單方式。」
>
> 追加：「最後一項是提醒交接的人，主管、老闆有沒有交代什麼事項是要注意的、
> 要待辦的，是不是也要列上去。」
>
> 當天確認的兩件事：
> - 來源 = **求助單 ＋ 待追蹤事項 ＋ 預約提醒**（任務卡這一版不收）
> - 按「補上」＝ **系統貼客觀事實 ＋ tag 他補一句現況**（不代替他做判斷）

## 這個功能在補什麼洞

現在的交接（v3.81）只確認「**有沒有打**」——
`ShiftHandoverService::detect()` 看到那一班的人在交接話題發言就算完成，
**內容一個字都沒看**。所以「沒有」兩個字就能結案，而那一班其實留著
三張沒人回的求助單。

這一版補的是「**打的內容夠不夠**」：系統手上本來就有那一班發生過什麼，
拿去跟他打的內容比對，漏掉的當場問他要不要補。

⚠ **不是在考核交接寫得好不好。** 只比對「這件事有沒有被提到」，
不評價寫得清不清楚 —— 後者沒有客觀標準，而且會讓這則通知變成找碴。

## 觸發時機：他打完交接的當下

掛在 `markHanded()` 之後，派 `HandoverReviewJob` 背景跑
（AI 要幾秒，webhook 不能等 —— 同 `ReplyTicketJob` 的理由）。

⚠ **不是等窗口結束才總結**：那時人已經下班了，補不動。
打完當下他還在現場，而且腦袋裡還有那一班的事。

⚠ **一個窗口只盤一次。** `markHanded()` 只在第一次發言時觸發
（之後 `status` 已是 `HANDED`，`findPendingForShifts()` 撈不到）——
他補充的第二句不會再觸發一輪新的比對，否則話題會被洗版。

## 要盤哪些事（需求方選定）

全部都限定在**上一班的回訊時段**內：`[date + 上一班回訊開始, window_end]`
（`window_end` 就是上一班回訊結束，表上已經有）。

| 來源 | 條件 | 為什麼是它 |
|---|---|---|
| 求助單 `auto_reply_ticket` | 那段時間開的，**到現在還沒結案**（`close_action` 是 null） | 「客人還在等」最直接的訊號 |
| 待追蹤事項 `conversation_followup` | 那段時間開的，現在還掛著 | 我方或客人說了「稍等」還沒給結果 —— 那本來就是承諾 |
| 預約提醒 `scheduled_reminder` | 那段時間排的、**還沒發出去**的 | 下一班要知道等一下會有東西跳出來，而那是上一班排的 |
| **主管／老闆交代的事** | — | **推導不出來**，見下節 |

⚠ **已經結案的不盤。** 那一班自己處理掉的事不需要交接 ——
列出來只會讓清單變長，而長清單沒有人看。

⚠ **每一種都設筆數上限**（`MAX_PER_SOURCE`，預設 5）。
一班開了 30 張單的那天，列 30 項等於沒列 —— 超過就在最後補一句
「另外還有 N 件，請自己到後台看」。

### ⚠ 最後一項是「問句」，不是資料

> 需求方：「最後一項是提醒交接的人，主管、老闆有沒有交代什麼事項是要注意的、
> 要待辦的，是不是也要列上去。」

**口頭交代、私訊交代，系統一個字都看不到。** 所以這一項不是從哪張表撈出來的，
是**固定掛在清單最後的一句提醒**：

```
4. 主管／老闆這一班有交代什麼要注意或待辦的嗎？
```

⚠ **它的「補上」行為跟前三項不一樣**：系統貼不出事實（根本不知道），
所以按下去是 tag 他請他自己打，而不是系統代貼。沒有的話回一句「沒有」。

⚠ **每一次都要出現，不管前三項有沒有漏。** 這一項的價值正是在
「系統完全不知道」的那一塊，用「這次沒別的漏項就不問」來省行數，
剛好省掉最該問的那一句。

## AI 比對

走既有的 `ClaudeCodeMatcher::generateStructured()`（Claude Code CLI，
訂閱制），輸入是他打的交接原文 ＋ 候選清單，輸出每一項
`covered` 與一句理由。

⚠ **只讓模型做「這件事有沒有被提到」這一件事。** 判斷標準寫在 system prompt：
講到同一個客人群組＋同一件事就算提到，用字不必一樣（「超商那個」
算提到「上游 API 新增超商」）。不要讓它判斷寫得夠不夠詳細。

⚠ **模型掛掉／沒設憑證時不要整個不發**（同其他幾支的原則）：
退成「沒有比對，這是這一班的全部清單」，選單照出。
少了過濾會多問幾項，但漏掉才是真的出事。

⚠ **候選一項都沒有時整個不發。** 那一班真的沒事 —— 發一則
「沒有漏掉的」只是噪音。但最後那一項（主管交代）**仍然要問**，
所以那時發的是只有一項的選單。

## 選單長什麼樣

```
📋 這一班有 3 件事看起來沒寫進交接（早班）

1. LV 群：上游 API 能不能自己新增超商
　　求助單 #123，已等 3 小時，還沒人回

2. TR 群：客人在等對帳單
　　待追蹤，2 小時前說「稍等」

3. 主管／老闆這一班有交代什麼要注意或待辦的嗎？

[1 補上] [2 補上] [3 補上]
[全部補上]  [都不用]
```

按下 `[1 補上]` → 系統在話題發一則，並 tag 他：

```
📝 補充交接（早班）

• LV 群：上游 API 能不能自己新增超商
　求助單 #123，已等 3 小時，還沒人回

@mary 麻煩補一句現在到哪了
```

按 `[都不用]` → 那幾項記成「他說不用」，訊息改寫成結果，不再追。

⚠ **沒有「催到補完」這回事。** 交接本身是催到完成的（v3.81，因為
「他沒有就會打沒有了」），但**漏項是判斷題** —— 他可能真的覺得那件事
不必交接。問一次就好，按不按由他。

⚠ 按鈕按完要 `editMessageText` 把選單換成結果，不要讓同一組按鈕留在那裡
被重複按（比照求助單那幾顆）。

## 為什麼需要一張新表

`callback_data` 只有 64 bytes，塞不下「哪一項、內容是什麼」。
所以比對結果要落地：`shift_handover_gap`

| 欄位 | 說明 |
|---|---|
| `shift_handover_id` | 哪一次交接 |
| `source_type` | 1=求助單 2=待追蹤 3=預約提醒 **4=主管交代（固定項）** |
| `source_id` | 來源主鍵（固定項為 null） |
| `summary` | 當下組好的摘要（**快照**，來源之後變了也不影響已發出的選單） |
| `covered` | AI 判定有沒有被交接到 |
| `status` | 0=待決定 1=已補上 2=他說不用 |
| `seq` | 在選單上的編號（`callback_data` 只帶 handover_id ＋ seq） |

⚠ `summary` 存快照的理由同 `auto_reply_ticket.question`：
按鈕可能半小時後才被按，那時單子早就被處理掉了，重查會查出不一樣的話。

## 實作時修掉的三件事（排版實測抓到的）

1. ⚠ **「另外還有 N 件」不能佔選單編號。** 第一版讓它跟其他項目一起進
   `shift_handover_gap`，結果選單變成 1、2、3、**5** —— 跳號看起來像系統壞掉
   （它沒有按鈕，所以編號 4 永遠不會出現）。改成在 `splitNotes()` 就抽出來，
   不進表、不送比對，附在清單最後。
2. ⚠ **補充交接那一則裡不能帶選單編號。** 「主管／老闆有沒有交代」那一項
   在選單上是「5.」，直接貼進交接內容會變成一個沒有上下文的編號，
   下一班看不懂。所以同一句話有兩個版本：`MANAGER_ASK`（選單，帶編號）
   與 `MANAGER_LINE`（補充交接，用 `•`）。
3. ⚠ **`mentionOf()` 不能回空字串。** 交接人查不到時那句會變成
   「　麻煩補一句現在到哪了」—— 開頭空一格，而且沒有人知道是在對誰說。
   退路三層：`@username` → 暱稱 → `handed_by_name` → 「交接的同仁」。

另外 `isOwner()` 與 `mentionOf()` 問的是同一個帳號（按一次按鈕會查兩次），
所以 `ownerOf()` 做了一個 per-request memo，比照
`UserRepository::$assignableForOwner`。**用 `array_key_exists` 而不是
`filled()`** 判斷查過沒 —— 查不到（null）也要記住，否則每次都會再確認一次
「還是查不到」。

## 稽核時再修掉的五件事（按 PROMPTS.md 逐項對照）

1. ⚠⚠ **「沒東西要比」被當成「比不出來」。** 那一班真的什麼事都沒發生時，
   候選只剩最後那句固定問話 ⇒ `$covered` 也是空的 ⇒ 第一版照 `blank($covered)`
   判斷，選單會印「這次沒辦法自動比對交接內容」——
   **那是在對一個好好交接完的人說謊**。改成 `filled($askable) && blank($covered)`。
2. ⚠⚠ **全都交接到時，標題說他漏了一件。** 那時清單只剩那句問話，
   而 `HEADER` 寫的是「有 1 件事看起來沒寫進交接」——
   指著一個**問句**說他漏了。加 `ALL_COVERED_HEADER`
   （「這一班的事都交接到了 👍　最後確認一件事：」），算數量時扣掉固定問話。
3. ⚠ **模型回的編號沒驗就用。** 它可能回清單外的編號（自己重編過的），
   那個 key 會對到另一個候選，把「其實沒交接到」的事標成已交接而
   **整項從選單上消失**。現在不在 `askable` 裡的一律丟掉並記 warning。
4. ⚠ **沒撈滿上限也去查總數**（第 2 節效能）：撈到的就是全部，那次 COUNT
   是白打的，三個來源各一次。`withMore()` 改吃 closure，只在撈滿時才問 DB。
5. 第 3 節字串插值：`buildKeyboard()` 的 `callback_data` 原本是
   `"{$prefix}:" . Arr::get(...) . ":{$id}"` 這種混合串接，改成先取值再整串插值。

另外補了兩處 log（第 5 節）：交接紀錄查不到、模型回了清單外的編號 ——
兩者都會讓選單默默少東西，沒有 log 就查不出為什麼。

## 驗證到哪

- DI 解析、選單／按鈕／補充交接三種排版、`splitNotes()` 的分流、
  大夜班跨日的區間起點（`date` 是 11/18、窗口在 11/19，起點要是
  **11/18 23:00**）都在本機用記憶體物件驗過
- **三種開頭各驗一次**（有漏的／全都交接到了／模型掛掉），
  以及 `withMore()` 的短路（撈 3 筆上限 5 ⇒ 0 次 COUNT；撈滿 5 筆 ⇒ 1 次）
  與 `askableIndexes()` 會跳過固定問話
- **`callback_data` 全部在 64 bytes 內**（`hr:f:7:1` 這種長度）
- ⚠ **沒有端到端跑過**：本機 dev 庫一筆求助單、待追蹤都沒有，
  也沒有真的交接訊息可以觸發 —— 模型比對那一段與 Telegram 送出要上線才看得到

## 待釐清

1. **「都不用」要不要記理由？** 目前只記狀態。之後若想看「哪些項目常常被
   認為不必交接」才需要，這一版不做。
2. **要不要讓下一班的人也能按？** 目前只有打交接的本人按得動
   （按鈕會驗 `from.id` 對不對得上 `handed_by_user_id`）——
   下一班按「補上」會變成他在替上一班承諾。

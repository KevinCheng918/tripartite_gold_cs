# 用 Telegram 指令查虛擬機

> 需求（2026-10-13）：「我如果說『幫我查一下LV_UAT虛擬機』或是『幫我確認lv-uat虛擬機規格』
> 或是『幫我查一下lv-uat虛擬機繳費了嗎』，這個的話查虛擬機都是回應，虛擬機價格、
> 開機或關機、是否繳費，未繳費的話，繳費日期是什麼時候」
>
> 補充：「都是站台，不會是機器名稱」
>
> 追加：「我要能得知虛擬機是否繳費、誰還沒繳錢、誰是開機還是關機，例如：
> 幫我查一下誰還沒繳錢、幫我確認lv-uat他是開機還是關機」
>
> 補充：「虛擬機不用列主機名稱，只需要列站台名稱就好」
>
> 再補充：「如果一個站有兩台，要分別列出，不能混在一起」

## 四種問法 → 四種回覆

| 使用者問的 | 意圖 | 回什麼 |
|---|---|---|
| 幫我查一下 LV_UAT 虛擬機<br>幫我確認 lv-uat 虛擬機規格<br>幫我查一下 lv-uat 虛擬機繳費了嗎<br>幫我確認 lv-uat 他是開機還是關機 | `station` | 該站台的完整卡片 |
| 幫我查一下誰還沒繳錢 | `unpaid` | 當月未收清單，跨站台 |
| 誰是開機還是關機 | `power` | 全部機器的電源清單 |
| 我 lv-uat 的點數夠扣這期的虛擬機費用嗎 | `afford` | 試算（見下方專節） |

⚠ **講了站台就一律回完整卡片**，不管他問的是規格、繳費還是電源 ——
需求方原話是「查虛擬機都是回應」這幾項，卡片本來就包含這些。
為「他問的是哪一項」再分支只是多一個會分岔的地方。

這條規則在 `VmQueryCommandParser::normalize()` **用程式收斂**，不只寫在 prompt
裡：模型偶爾會回「intent=power ＋ station=LV_UAT」，`station` 填了就一律當
`station` 意圖。

## 不列主機名稱，但一台一段 → 用序號

需求方給了兩條看起來打架的規則：

1. 「虛擬機不用列主機名稱，只需要列站台名稱就好」
2. 「如果一個站有兩台，要分別列出，不能混在一起」

合起來就是：**分台列，但用序號代替主機名**。

⚠ **第一版做錯了：我做成加總。** 只看到第 1 條就推論「沒有名字就分不出哪行
是哪台，所以要加總」—— 加總把兩台不同的規格與電源壓成一行，資訊直接弄丟。
序號才是那個缺的識別，不是把明細收掉。

```
🖥 LV_UAT 的虛擬機（3 台）

① 規格：2C4G 50GB
　 費用：45.00 USDT／月
　 　（主機 30.00　VPN 10.00　Google 5.00）
　 電源：🟢 開機
　 10 月帳單：❌ 未收 45.00 USDT，應收日 10/5（已逾期 8 天）

② 規格：4C8G 200GB
　 費用：80.00 USDT／月
　 電源：🔴 關機（9/20 起）
　 10 月帳單：關機不出帳

③ 規格：2C2G 20GB
　 費用：25.00 USDT／月
　 電源：🟢 開機
　 10 月帳單：⏳ 客戶已上傳繳款證明，等後台審核（25.00 USDT）
```

細節：

- **只有一台時不編號也不縮排** ——「①」後面沒有②，那個序號只會讓人以為
  還有別台沒列出來
- **超過十台沒有圈號可用**，退回 `(11)`。直接取陣列第 11 個會拿到 null，
  那一行的序號就不見了
- **費用拆帳**只有主機費時不拆（「VPN 0.00　Google 0.00」是雜訊）
- 一台一個月只會有**一筆**帳單（`vm_billing` 的 unique 是
  `vm_server_id` ＋ `billing_month`），所以帳單是單行不是清單

⚠ 費用的組成跟產帳單那邊一樣（主機 ＋ VPN ＋ Google，見
`VmService::generateMonthlyBillings()`）—— 這裡報的數字必須跟實際出帳對得起來。

### 跨站台清單也要編號

「誰還沒繳錢」「誰開機誰關機」是一筆一行，同一個站台有兩台時兩行會長得
**一模一樣**（因為不列主機名），看的人會以為系統列重複了。

所以先數一遍，**同一站真的有多台才加序號**：

```
🟢 開機（2 台）
• LV_UAT ①
• T01            ← 只有一台，不編號

🔴 關機（1 台）
• LV_UAT ②（9/20 起）
```

## 「點數夠不夠扣這期虛擬機費用」（`afford`）

> 需求（2026-10-13）：「我如果問『我 lv-uat 的點數夠扣這期的虛擬機費用嗎』，
> 應該要先去查看這期繳費了沒，然後再確認虛擬機費用，然後再確認站台點數，
> 然後再試算，試算完回報說，虛擬機這一期價格、目前點數、試算完剩多少」

邏輯放在 `app/Services/VmAffordabilityService.php`，不放在 Telegram 那支裡 ——
錢的算術值得自己一個地方。

### ⚠ 單位不一樣，一定要換算

| | 單位 |
|---|---|
| 虛擬機費用 | **USDT**（繳款通知與 VPN 續約通知都明寫） |
| 站台餘點 | **點** |

補點那邊的關係是「USDT ＝ 點數 ÷ 匯率」（`TOPUP_USDT_BASE` 的註解），
反過來就是 **點數 ＝ USDT × 匯率**。

本機實測匯率 **32.174**，所以 800 USDT ≈ **25,739 點**，不是 800 點。
直接拿 800 比 800 會差三十幾倍 —— 會回「夠扣」但其實遠遠不夠，
而這個答案正是拿來決定要不要補點的。

### 匯率來源與退路（需求方指定）

1. 今天決定的對客報價（`DailyRateService::todayRate()`）
2. 還沒決定 → **4H 均價**（`UsdtRateService::getRateWithHistory()` 的 `avg_rate`）
3. 都拿不到 → **照實說算不出來**，並把兩個原始數字列出來，標明單位不同不能直接比

⚠ **不退到昨天的匯率** —— 比照 `DailyRateService::customerAnswer()`
（寧可請對方稍候也不給過期匯率）。

⚠ **回報一定要寫用的是哪一個**。今日報價與 4H 均價是兩個不同的數字，
看的人得知道這是定案的還是浮動的。

### 七種結果各有各的話

```
🧮 LV_UAT 這期虛擬機費用試算

這期費用：800.00 USDT（1 台）
換算匯率：32.5（今日報價）
需要點數：26000.00
目前點數：40000.00（10/13 18:19 同步）

✅ 夠扣，扣完剩 14000.00 點
```

| 結果 | 回什麼 |
|---|---|
| `ok` 夠／不夠 | 上面那張（不夠時講「還差 N 點」） |
| `pending` | 同上，另加一行「這期客戶已上傳證明等審核」 |
| `paid` | 「這期已經收了，不用扣點」—— 不試算 |
| `no_billing` | 「這期沒有帳單（關機不出帳，或還沒產）」 |
| `sync_failed` | 「查不到現在的點數，沒辦法試算」，**不拿舊點數算** |
| `no_rate` | 列出兩個原始數字，說明單位不同不能比 |

⚠ **算不出來就說算不出來，不要湊數字。**

### 這一支會同步點數，而且沒有二次確認

用資料庫裡那個點數來判斷「夠不夠扣」正是餘點告警一直在防的事
（`SKIP_SYNC_FAILED`），所以一定要先同步。

⚠ 但同步會打主系統 API ＋ 寫 DB —— [[station-credit-command]] 正是為此做了
二次確認。這裡**沒有**，因為需求方描述的流程是一氣呵成的
（「先查繳費了沒 → 再確認費用 → 再確認點數 → 再試算」），
而使用者要的是一個試算結果，同步只是取得結果的必要步驟。
**要改成先確認的話，加一顆按鈕就好。**

先回一句「正在同步並試算，請稍候…」，不然 API 那幾秒會像沒反應。

### 權限要兩個

`telegram_chat.vm_query` **＋** `telegram_chat.station_credit`。

⚠ 這個答案裡**有站台餘點**。只驗虛擬機那個的話，問「夠不夠扣」就成了
繞過餘點權限的側門。

### ⚠ 餘點解析器原本會把這題搶走（上線前抓到）

餘點排在虛擬機**之前**，而「我 lv-uat 的點數夠扣…」裡有「點數」——
實測餘點解析器回 `credit`／`lv-uat`，使用者會拿到餘點確認按鈕而不是試算。

病根是**餘點解析器過度認領**：「告訴我餘額」與「拿餘額去比對一筆費用」
是兩件事。改的是餘點的 prompt（加一句「拿點數跟某筆費用比較、問夠不夠的
填 not_credit」），不是調順序 —— 靠順序解只是把問題藏起來，下次加指令又會撞。

修完實測：

| 說的話 | 餘點解析器 | 虛擬機解析器 |
|---|---|---|
| 我lv-uat的點數夠扣這期的虛擬機費用嗎 | `not_credit` ✓ | `afford` ✓ |
| LV_UAT 餘點付得起這個月的機器錢嗎 | `not_credit` ✓ | `afford` ✓ |
| 幫我查一下LV_UAT餘點 | `credit` ✓ | `not_vm` ✓ |
| 確認Rich還剩多少點 | `credit` ✓ | — |
| 幫我查一下LV_UAT虛擬機 | `not_credit` ✓ | `station` ✓ |

## 繳費是三態，不是「是／否」

`config('constants.VM.BILLING')`：

| 值 | 常數 | 意思 |
|---|---|---|
| `0` | UNPAID | 未收 |
| `2` | **PENDING** | **客戶已上傳繳款證明，等我們後台審核** |
| `1` | PAID | 已收 |

⚠ **`2` 絕對不能講成「未繳費」。** 客戶已經付錢也上傳證明了，卡在我們這邊
沒人審 —— 回「未繳費」是把我們的延誤說成客戶的欠款，而且會去催錯人。

三種分開講：

```
❌ 未收 800.00 USDT，應收日 10/1（已逾期 12 天）
⏳ 客戶已上傳繳款證明，等後台審核（800.00 USDT）
✅ 已收 800.00 USDT（10/3）
```

跨站台清單也一樣：待審核的那筆**要列進來**（錢確實還沒入帳）但**分開標示**。

## 關機不出帳

`generateMonthlyBillings()` 只對開機的機器產帳單（「開機才收錢」）。
所以關機的機器沒有當月帳單 —— 這時要說「關機不出帳」，不是「這個月還沒有帳單」。

⚠ 判斷順序：先看**有沒有帳單**，沒有再看**電源**。反過來寫的話，
關機前就產好的帳單會被「關機不出帳」蓋掉，那筆錢還是要收的。

## 只看當月（需求方決定）

帳單只查當月（`now()->format('Y-m')`），不翻舊帳。

⚠ 已知取捨：積欠三個月時只會看到一個月，看起來像只欠一筆。
當初的另一個選項是「全部未收都列」，需求方選了當月。

## 站台名稱比對：抽成共用的 `StationNameMatcher`

需求的三句話裡同一個站台寫了 **`LV_UAT` 也寫了 `lv-uat`**。餘點指令原本是
「不計大小寫的完全相符」，`lv-uat` 會找不到 `LV_UAT`。

抽出 `app/Services/StationNameMatcher.php`，四支指令共用：

- **`_`、`-`、空白、全形空白視為同一件事**，大小寫不計
  （`LV_UAT` ＝ `lv-uat` ＝ `LV UAT` ＝ `lvuat`）
- 正規化之後**仍然要完全相等**，不做模糊比對 —— `LV` 不會命中 `LV_UAT`
- `mentioned()` 數「這串字裡出現幾個已知站台名」，用來分辨
  「講了兩個站台」與「名字不存在」

⚠ `mentioned()` **只能用來數個數**。站台有 `T01` 沒有 `T011` 時，問 `T011`
會「包含 T01」—— 拿去查就回了另一個站台的數字。所以命中一個時仍走「找不到」。

⚠ `dropContained()`：同時有 `T01` 與 `T011` 時，字串 "T011" 包含兩者，
不排掉會被數成「講了兩個站台」。

本機實測（站台：`測試`、`LV`）：

| 輸入 | match | mentioned |
|---|---|---|
| `LV` / `lv` / `l-v` / `L_V` / ` lv ` | `LV` | `[LV]` |
| `測試` | `測試` | `[測試]` |
| `LV、測試` | null | `[測試, LV]` → 回「一次只能查一個」 |
| `LVX` | null | `[LV]`（1 個）→ 回「找不到」，**不猜 LV** |

## 不做二次確認

| | 餘點指令 | 虛擬機 `station`／`unpaid`／`power` | 虛擬機 `afford` |
|---|---|---|---|
| 資料來源 | 打主系統 API | 只讀自己的 DB | **兩邊都要** |
| 會寫入嗎 | 會 | **不會** | **會**（同步點數） |
| 要等嗎 | 要（幾秒） | 不用 | 要（幾秒） |
| 二次確認 | **要** | **不用** | **不用**（理由見上方專節） |

前三種純讀本地資料、沒有副作用、不用等，多一次點擊只是礙事。

⚠ `afford` 是例外：它跟餘點指令一樣會同步、會寫入，卻**沒有**二次確認。
那是需求方描述的流程使然（一氣呵成的試算），不是疏漏 —— 詳細理由與
「要加按鈕怎麼加」寫在上面的 `afford` 專節。

## 權限：`telegram_chat.vm_query`

介面上：**帳號管理 → 編輯帳號 → 權限設定 → Telegram 客服 → 用指令查虛擬機**。

⚠ `afford` 另外**多要** `telegram_chat.station_credit`（答案裡有餘點），
見上方專節。

- 不沿用後台的 `vm.view`：照 [[station-credit-command]] 的教訓，
  「後台檢視虛擬機」與「用指令查一下」是兩件事
- 也不跟 `telegram_chat.station_credit` 共用：餘點是**客戶在主系統的錢**，
  虛擬機費用是**我們向客戶收的錢** —— 敏感度不一樣，誰能看該分開指派

⚠ 管理者（admin）bypass 所有權限檢查（`User::hasPermission()` 第一行），
所以用 admin 帳號測不出這道關卡。

## 待釐清 / 已知缺口

- **本機資料量極小**（`vm_server` 1 台、`vm_billing` 3 筆，沒有關機的機器、
  沒有待審核的帳單）。「一站多台」「關機不出帳」「⏳ 待審核」「跨站台清單的
  序號」這幾條路是用**記憶體裡組出來的 model**（不寫 DB）渲染驗過的 ——
  版面與分支正確，但沒有真資料從查詢端走完整條路。
- **沒有綁定 Telegram 的帳號**，所以權限通過之後的完整流程沒有端到端測過。
- 清單上限 20 筆，超過會顯示「…另外還有 N 筆」。目前資料量遠低於上限。

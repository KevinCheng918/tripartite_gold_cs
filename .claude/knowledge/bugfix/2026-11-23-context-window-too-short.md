# 客人回答我們的提問，小幫手卻回「已經請專員為您確認」

> 需求方 2026-11-23：「這邊是客服人工去詢問進度，然後對方回應明天處理，
> 不應該回覆請專員確認才對。」
>
> 追加 2026-11-24：「對話脈絡不應該侷限寫死 15 分鐘，應該要看他是否有引用
> 哪句話，或是前一段訊息在講什麼，往回去看，**不然都有一種笨笨的
> 判斷力不好的感覺**。」

## 線上實際經過

| 時間 | 誰 | 內容 |
|---|---|---|
| 13:11 | 我方同仁（人工，署名 -E） | 「老闆您好，請問目前超商通道設定上還順利嗎，有什麼需要協助的部分嗎？」 |
| **23:52** | 客人 | 「明天設定」 |
| 23:52 | 小幫手 | 「老闆，明天設定這部分已經請專員為您確認，再麻煩您稍等一下。 -A」 |

客人是在**回答我們**，不是在**問我們**。

## ⚠⚠ 我第一次判錯了成因 —— 客人**沒有**引用

第一版（v4.03）以為客人是引用我方那一則回的，所以去修「引用沒送進脈絡」。
**需求方更正：客人是直接打字回的。**

（截圖上「明天設定」旁邊的 ↩1 是 Telegram 的**回覆計數**
——「有 1 則回覆」，指的是小幫手回了它；不是客人引用了我們。）

v4.03 本身仍然是對的改進（引用確實一直沒送給模型），但它**救不到這一案**。

## 真正的成因：脈絡寫死 15 分鐘

```php
// config/auto_reply.php（修正前）
'context' => [
    'limit'   => 6,
    'minutes' => 15,   // ← 只看最近 15 分鐘
],
```

同仁那則問話是 **13:11**、客人 **23:52** 才回 —— 隔了 11 小時，
`getRecentMessages()` 的 `where created_at >= now()-15min` 把它整個濾掉。

**模型收到的就只有「明天設定」四個字。**

那四個字單獨看**確實**判斷不出來，所以它照 schema 的指示填
「分不出來就 unclear」⇒ 轉人工 ＋ 承接話術。
⚠ **它做的是對的事，錯在我們給的資訊不完整** ——
需求方說的「笨笨的判斷力不好的感覺」，來源是這裡。

## 修法：時間不再用來判斷相關性

| | 修正前 | 修正後 |
|---|---|---|
| 則數 | 6 | 6（不變） |
| 時間 | `minutes: 15`　**用來切相關性** | `max_hours: 24`　**只擋「翻到好幾天前」** |
| 相關性誰判 | 我們（硬切） | **模型**（每行標「多久以前」） |

```
（11 小時前）客服：老闆您好，請問目前超商通道設定上還順利嗎… -E
（剛剛）客人 西瓜汁：明天設定
```

⚠⚠ **相關性交給模型判斷，不要我們硬切。** 它看得到「這是 8 小時前的事」
就會自己掂量要不要採用；而我們切的那一刀**永遠會切錯一邊** ——
15 分鐘就是切錯的那一刀。

⚠ `agoLabel()` **自己算，不用 `diffForHumans()`** —— 那一支吃 app locale，
英文環境會吐 "11 hours ago"。這段文字是送進模型的，不該跟後台語系綁在一起。

⚠ **`run_minutes`（15）是另一件事，沒有動。** 那是「客人正在把一句話拆成
好幾則打」的合併窗（`getConsecutiveInbound()`），單位是分鐘而且該短。
兩個設定長得像，但一個問「前面聊過什麼」、一個問「這一輪講完了沒」。

### 另外在判斷規則裡補兩條

`buildSchema()` 的 `intent` 說明：

1. 客人若是在**回答我方先前的提問**（我方問「設定上還順利嗎」、他回
   「明天設定」「好」「處理中」），那是 `chat` ——「他在回答我們」
   不是「他在問我們」，不要轉人工。
2. 每行開頭的「（N 小時前）」是給它判斷相關性用的：隔得久的不一定還相關，
   **但也不要因為隔得久就忽略** —— 我方問完、客人幾小時後才回很常見。

## v4.03 那一半（引用）：仍然保留

客人**真的有引用**時，那一則會被接到脈絡最前面，而且**不受 24 小時上限**
—— 客人指著哪一則，那一則就是他的上下文，隔多久都一樣。

⚠ 還會標明那一則是**我方**還是**別的客人**說的：判斷方式是
`reply_to_message.from.id` 對上 `getBotId()`（人工與自動都走同一支 Bot）。
⚠ 要用 `getBotId()` 而不是設定檔的預設 token（上面已 `switchBotToken()`），
否則非預設 Bot 的群組會全部判成「不是我方的」。
⚠ 這件事**只有 webhook 那一刻比得出來**，所以走 Job 參數傳遞、不從 DB 撈
（表裡只存了引用的文字與暱稱，沒存「那一則是誰的」）；`AutoReplyJob` 的
新參數要 `(array)` 轉型，否則升版那一刻佇列裡在飛的舊 Job 反序列化成 null
會丟型別錯誤。

## 驗證到哪

`agoLabel()`：剛剛／1 分鐘前／45 分鐘前／1 小時前／2 小時前／11 小時前／
1 天前／3 天前／時間不明（null）。

重現線上那一案（交易內 rollback，客人**沒有**引用）：

```
[1] （11 小時前）客服：老闆您好，請問目前超商通道設定上還順利嗎… -E
—— 撈到 1 則
11 小時前那則問話有進來嗎？ yes ✓
30 小時前那則有被擋掉嗎（超過 24 小時）？ yes ✓
```

`withQuote()` 六種情況：我方／別的客人標籤正確、已在脈絡裡不重複貼、
無文字與無引用不動脈絡、換行壓成一行。

⚠⚠ **「模型那一側驗不到」這句話是錯的**（2026-11-24 更正）。

當時我在 `docker-compose exec workspace` 裡測，得到 `claude: not found`
就下了那個結論 —— 但 **workspace 沒有 CLI、php-fpm 有**
（`/usr/local/bin/claude`），而網頁請求本來就走 php-fpm。
見 [[dev-environment]]。

所以「補上脈絡之後它會不會真的改判 `chat`」**是驗得到的**，
只是當時沒驗（入口用錯了）。這次修的是「把它該看到的東西給它」——
判斷仍然是模型做的，而那一段**仍然沒有實測過**。

⚠ 要觀察兩件事：①同情境還會不會回承接話術 ②脈絡變長之後，
**會不會反過來用幾小時前的事去解釋現在這句話**（過度關聯）。
後者是這次改動真正的新風險。

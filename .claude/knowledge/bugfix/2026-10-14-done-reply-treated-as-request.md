# 客人說「已完畢！」被回「已請專員接手跟進」

> 客人（引用回覆我們的訊息）：「已完畢！」
>
> 系統回：「老闆收到您的訊息了，這邊已請專員接手跟進，再麻煩您稍等一下。 -A」
>
> 需求方：「對方說已完畢，不應該回專員接手」

**根本沒有東西要跟進** —— 客人只是回報他做完了。回這句話等於叫他再等一次，
而且等不到任何東西。

## 重現

無上下文時其實是對的：

```
已完畢！  →  intent=chat ｜ opening='好的，感謝老闆告知～'   ✓
```

但截圖裡客人是**引用回覆**，所以有上下文。帶上下文就壞了：

```
<前面的對話>
客服：…麻煩您到後台重新設定一次，設定完再跟我們說一聲
</前面的對話>
<客人的問題>
已完畢！
</客人的問題>
  →  intent=request   ✗   （→ WAIT → 轉人工 → 那句「已請專員接手」）
```

⚠ **沒有上下文時測不出這個 bug。** 判斷錯誤只在「客人回覆我們」的情境發生，
而那正是實務上最常見的情境。

## 病根：規則寫得太寬

`ClaudeCodeMatcher::buildSystemPrompt()` 裡原本寫：

> 他貼上帳號、密碼、API KEY、網址、訂單號、ID、一整段設定值，
> **或是在回答我們先前問他的事情** —— 這些資料是要給同仁去處理的，一律轉人工

那條規則本身是對的（客人把資料給我們卻被當寒暄略過，他會以為沒收到）。
問題出在「**或是在回答我們先前問他的事情**」—— 太寬了。

「已完畢！」確實是在回答我們，但它**沒有帶任何要同仁處理的內容**。

## 修法：把判準換掉

判準不是「他是不是在回答我們」，而是「**這句話裡有沒有東西要同仁處理**」。

prompt 補上反向規則與對照例：

| 客人說 | 有東西嗎 | intent |
|---|---|---|
| 我帳號是 abc123 | 有（帳號） | `request` |
| 訂單號 20261014001，麻煩查一下 | 有 | `request` |
| **已完畢！** | **沒有，只是回報做完了** | **`chat`** |
| **好了，我設定完成了** | 同上 | **`chat`** |

並明講這一類「**不要**說『已請專員接手』『已轉給專員』—— 沒有東西要接手」。

## ⚠ 改這段 prompt 之後要清快取

整份 system prompt（規則 ＋ 題庫）存在 `Cache` 裡：

```php
Cache::remember(config('auto_reply.prompt_cache_key'), ...)   // auto_reply.prompt.v4
```

- **`php artisan optimize` 清不掉**（那是 config 快取，這是 Cache 條目）
- TTL 300 秒，所以正式機**最多等 5 分鐘**會自己生效
- 要立刻生效：`Cache::forget(config('auto_reply.prompt_cache_key'))`，
  或在後台改一次題庫（`QuickReplyService` 會主動清）

第一次重 dump prompt 時長度一模一樣（48446 bytes）就是卡在這裡 ——
**以為沒改成功，其實是讀到快取**。

## 驗證（本機 CLI，2026-10-14）

修正後：

| 情境 | 結果 |
|---|---|
| 請他做事 → 他回「已完畢！」 | `chat`／「好的，辛苦老闆了～」✓ |
| 跟他要資料 → 他回「已完畢！」 | `chat`／「好的，辛苦老闆了～」✓ |
| 好了／處理好了／設定完成了／我知道了／收到／OK 用好了 | 全部 `chat` ✓ |

回歸（原規則不能壞，同樣帶「跟他要資料」的上下文）：

| 客人說 | 結果 |
|---|---|
| 我帳號是 abc123 | `request` ✓ |
| 訂單號 20261014001 | `request` ✓ |
| abc123 / 20261014001 麻煩查一下 | `request` ✓ |
| 手續費怎麼算的（無上下文） | `question` ✓ |

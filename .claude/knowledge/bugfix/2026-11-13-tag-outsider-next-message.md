# 客人 tag 完自家同事，下一句是講給同事聽的，小幫手還是回了

> 客人群組（對方主管 RM）：
> 21:32 一則只有 `Amy 2.0` 的訊息（把自家同事叫進來）→ 擋掉了 ✓
> 21:32 緊接著「所有人給你嗎？」→ **小幫手回了**
> 「老闆，Amy 2.0 的開通範圍已經請專員為您確認，再麻煩您稍等一下 -A」
>
> 需求方 2026-11-13：「雖然剛開始是 tag 機器人，但是後來他 tag 了另一個人
> 要處理其他事情，這時候機器人不應該回覆。」

這是 [[2026-10-27-tag-only-message-auto-replied]] 的續集 —— 那次上線的
`isTagToOutsidersOnly()` **判得是對的，只是涵蓋範圍差一則**。

## 根因：人不會把 tag 跟話塞在同一則

10/27 那道判斷的前提是「整則都是 tag」。但實際的講話順序是：

```
[RM] Amy 2.0            ← 整則都是 tag，擋掉 ✓
[RM] 所有人給你嗎？      ← 這句才是要問同事的，沒有 tag，照常回了 ✗
[RM] 管理員              ← 同上
```

**真正該擋的是後面那幾句**，而它們身上一點 tag 的痕跡都沒有。
再加上自動回覆會帶 15 分鐘內的對話脈絡進模型，模型看得到上一則的
`Amy 2.0`，於是憑空生出「Amy 2.0 的開通範圍」這種客人沒問過的事。

> 補充：被叫的人沒有 username，所以那一則是 `text_mention`（文字裡沒有 `@`）。
> 這部分 10/27 已經處理好了 —— 擋住第一則的正是 entity 判斷，
> 問題不在認不認得出 tag。

## 修法：一段「跟外人講話」的靜默

`TelegramChatService::isTalkingToOutsiders()` 取代原本直接呼叫
`isTagToOutsidersOnly()` 的第 4 道閘門，內容是同一件事的前後兩段：

1. 這一則整則都是 tag 外人 → 擋，並記一個**逐對話、逐發話者**的快取標記
   （`auto_reply.tag_outsider.{group}.{user}`，TTL = `auto_reply.tag_outsider_silence`，預設 60 秒）
2. 標記還在的期間，同一個人講的話一律不自動回覆

## ⚠ 靜默必須有出口，否則是黑洞

客人 tag 完同事**再回頭問我們**非常常見。被靜默的訊息不會自動回覆、
也不會開求助單 —— 那正是 [[2026-11-08-silent-black-hole]] 的形狀。
所以三道出口一個都不能少：

- **60 秒就過期**，而且擋掉的訊息**不續約**（不會把時間一路往後推）。
  60 秒是「講完那幾句」的長度，不是「聊完那件事」的長度
  （第一版填 90 秒，需求方 2026-11-13 當天就說太長 —— 偏長的那一側是
  「客人真的在問我們卻被吃掉」，比偶爾多插一句話嚴重）
- 這一則 **tag 了我方的人或機器人** → 當場 `Cache::forget`，照常回覆
- 這一則 **引用回覆我方發出去的訊息** → 同上

## ⚠ 標記要綁 Telegram user id，不能只綁群組

群組裡同時有好幾個客人講話是常態。綁群組的話，A 把同事叫進來會把 B
真正的問題一起吃掉。拿不到 user id 時**寧可不記**（用 0 當 key 等於綁群組）。

## ⚠ 順序：先看快取，再看 tag

`inTagOutsiderSilence()` 第一件事是 `Cache::has()`，沒命中就結束。
解除條件裡的 `tagsOurSide()` 會查 Bot 自己的 username（可能打 Telegram API，
快取一天），絕大多數訊息根本走不到那裡。

## ⚠ 機器人自己要比 username，不是比 user id

`repliesToOurSide()` 判斷「引用的是不是我們發的」時：我方同事的 id 查得到
（在 `user` 表），**機器人不是後台帳號，查不到**，只能比 username。
也不能只看 `is_bot` —— 客戶群組裡常常還有對方自己的機器人。

## 沒有改的地方

- `isTagToOutsidersOnly()` 本身一行沒動。它的語意（**只看這一則**）是乾淨的，
  把狀態混進去會變得很難推理 —— 靜默窗是外面包一層
- 沒有改 prompt。「這句是講給誰聽的」在結構上判得出來，不要交給模型猜
  （理由同 10/27 那份）

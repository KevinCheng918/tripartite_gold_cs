# 上傳了繳款證明，還是被催「麻煩協助手動通知客戶繳款」

> 需求方：「我虛擬機有上傳證明但未審核的話，他還是傳送原因：這個站台沒有設定
> Telegram 群組，麻煩協助手動通知客戶繳款，可是他明明是未審核，應該要審核才對」
>
> 追問確認：**同一個月**，而且**完全沒收到**那則「繳款證明還沒有人審核」。

## 查到哪裡

那段文字只有一個來源：`VM.NOTICE.INTERNAL_PREFIX`，而它只由
`handleUnpaidBilling()` 送出 —— 那條路只吃 `getBillingsForNotice()` 撈出來的
帳單，條件是 `paid = UNPAID`。

所以**排程跑的當下那筆的 `paid` 就是 0**。實測兩條路都驗過：

```
paid=2 → ⏳ 繳款證明還沒有人審核…
paid=0 → 🔔 …沒有發給客戶 / 原因：這個站台沒有設定 Telegram 群組…
```

排除過的可能：

- 上傳證明**只有一條路徑**（`VmService::uploadProof()`），它一定寫 `paid = 2`
- 那支裡抓匯率的呼叫**不會丟例外**（`UsdtRateService` 內部自己 catch，
  最壞回 0），不會「檔案存了但狀態沒寫」
- `VmBilling` 的 `$guarded = ['id']`，`paid` 可以 mass assign，不是被擋掉
- 全專案**沒有任何地方**把 `paid` 寫回 0（只有 0→2、2→1、→1）
- 後台的「手動發送繳款通知」是發給指定客戶群，不產生這則訊息

也就是說，照現有程式碼，`proof_image` 有值而 `paid = 0` **不該發生**。
真正怎麼變成那樣（手改資料庫？某次部署中途的狀態？）無從回推。

## 修法：不要只信一個欄位

重點不是「怎麼變成那樣」，而是 **`paid` 跟「有沒有證明」是兩個訊號，程式只看
了一個**。它們一旦分家，客戶就會被催一筆他已經付過、證明還躺在我們後台的款。

需求方講的規則才是對的：**有上傳證明就該去審核，不該催客戶**。所以兩張清單
都改成看兩個訊號：

| 狀態 | 去哪 |
|---|---|
| `paid=0` ＋ 沒證明 | 催客戶 |
| **`paid=0` ＋ 有證明** | **催審核**（原本落在催客戶） |
| `paid=2` | 催審核 |
| `paid=2` ＋ 沒證明 | 催審核 |
| `paid=1` | 都不發 |

⚠ **兩邊要一起改。** 只在 `getBillingsForNotice()` 排除「有證明」的話，
`paid=0 ＋ 有證明` 那一筆會從**兩張清單上同時消失** ——
客戶付了錢、證明躺在後台，而沒有任何人被通知。比原本更糟。

所以 `getPendingBillingsForReminder()` 也改成
`paid = PENDING` **或** （`paid = UNPAID` 且有證明）。

⚠ `orWhere` 一定要包在 closure 裡，不然會把外層條件一起 or 掉。
產出的 SQL 確認過：

```sql
-- 催客戶
where `paid` = ? and (`proof_image` is null or `proof_image` = ?)

-- 催審核
where (`paid` = ? or (`paid` = ? and `proof_image` is not null and `proof_image` != ?))
```

## 一般化

**「狀態欄位」與「事實」分家時，要以事實為準。**

`paid` 是我們自己維護的狀態，`proof_image` 是客戶真的做過的事。狀態可能因為
任何原因沒跟上，但「他上傳了證明」這件事是真的 —— 拿狀態去否定事實，
受害的是客戶。

這跟餘點告警「同步失敗絕不拿舊點數判斷」是同一條：**寧可不做，也不要根據
可能過期的狀態去對客戶做事。**

## 待確認

根因還沒找到。如果之後又出現，要看的是那筆 `vm_billing` 的
`paid` / `proof_image` / `updated_at` 三欄 —— 現在至少不會再催到客戶，
而是會出現在催審核那張清單上，有人會看到。

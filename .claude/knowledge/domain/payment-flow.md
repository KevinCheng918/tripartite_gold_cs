# 三方金流背景知識（代收/代付）

`tripartite_gold_cs` 是「tripartite_gold」三方金流主系統的技術客服子系統，服務對象（商戶、代理）與資料模型與主系統共用，因此客服人員與開發需理解以下資料流：

## 代收/代付四層架構

- **L1**：商戶開單到四方站台（`user.level=2` 呼叫 API）
- **L2**：四方站台打到第三方通道（Apollo）
- **L3**：第三方通道回調四方站台
- **L4**：四方站台回調給商戶

⚠️ **一般情況下只有 L1 與 L4**。只有在該筆訂單走第三方支付通道時
（例如黑貓等），才會多出 L2 與 L3。

所以看到客人只貼得出 L1 與 L4 的 log 是正常的，不代表資料不完整；
反過來說，**有 L2／L3 就表示這筆確實送到第三方了**，
這是判斷「訂單有沒有出去」最直接的依據。

### 客人貼 log 來問時，先確認是哪一段

站台轉述商戶的問題時常直接貼 API log。**先分清楚是哪一段**，
才知道訂單有沒有送到第三方、問題出在誰身上：

| 症狀 | 要看哪一段 | 判斷 |
|------|-----------|------|
| 開單就失敗 | **L1** 商戶 → 站台 | 訂單根本沒送到第三方，多為參數或加簽問題 |
| 建單成功但一直待處理 | **L2 / L3** | 尚未送到第三方，或第三方還沒回覆 |
| 訂單已完成但商戶沒收到通知 | **L4** 站台 → 商戶 | 多為商戶的回調網址無法連線或沒回 OK |

實際案例：客人曾貼過兩段 log，url 分別是 `/api/withdraw`（**L1**）
與商戶端的 `ServerCallback`（**L4**）。從 L4 的 `status` 就能判斷該筆代付的最終結果 ——
這種情況整條鏈路其實是通的，只是該筆被判失敗。

## 訂單狀態碼

來源：主系統 `config/constants.php` 的 `PAYMENT.DEPOSIT_STATUS` / `WITHDRAW_STATUS`。

| 狀態碼 | 代收（DEPOSIT） | 代付（WITHDRAW） |
|--------|----------------|-----------------|
| `00` | 待付款 | 待付款 |
| `01` | 成功 | 成功 |
| `02` | **群組單成功** | **失敗** |
| `03` | 失敗 | — |

⚠️ **同一個 `02`，代收是成功、代付是失敗。** 看到 `02` 一定要先確認是哪一種單，
不然會把失敗的代付告訴客戶「已成功」。

## 商戶訂單號格式

來源：主系統的 `ApiDepositApplyRequest` / `ApiWithdrawApplyRequest`。

| | 允許的字元 |
|---|---|
| 代收 | `^[A-Za-z0-9\-]{10,50}$` → 連字號 `-` |
| 代付 | `^[A-Za-z0-9\_]{10,50}$` → 底線 `_` |

⚠️ **兩者不一樣。** 商戶代收慣用的 `abc-123` 拿去送代付會被判格式異常，
而代付的錯誤訊息只寫「商戶訂單號格式異常」，沒說原因 —— 客人常常卡在這裡。

## 群組單（僅代收適用）

- `bank_data_json` 欄位以 `_` 分隔多組銀行資訊
- 子單 sn 格式：`{主單sn}_{index}`

## 適用場景

客服在處理商戶申訴、對帳問題、Telegram 對話視窗中的訂單查詢時，需依此四層鏈路判斷卡在哪一層（L1 建單失敗 / L2-L3 轉單逾時 / L4 回調失敗）。
